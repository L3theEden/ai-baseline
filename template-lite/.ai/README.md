# 需求分析精简基线

本目录只服务三个任务：核实卡内容、整理给 BA 的问卷、回填答复并整理需求结论。使用当前工作区的代码快照，只写卡片文档。

## 使用顺序

1. `card-intake` + 卡号与原文：执行 [读卡说明](workflow/01-card-intake.md)，产出 `README.md`、`01-card.md`。
2. `clarify <卡目录>`：执行 [问卷说明](workflow/02-clarify.md)，默认先与用户交互澄清，每轮复核后把待 BA 决定的部分整理为 `02-questions.md`，由用户审阅再自行转发；明确要求直接出问卷时可跳过访谈。
3. `align <卡目录>` + BA 回复：执行 [回填说明](workflow/03-align.md)，回填问题并维护 `03-alignment.md`。答复不全时继续追问，关键问答收敛后结束。

问卷是按轮维护的产物。每批答复后复核新问题、依赖、冲突和验收缺口，有需要就回到 `clarify`；产出文档或答满当前问题列表都不等于分析结束。

也可直接说“读这张卡”“整理问 BA 的问卷”“回填这些答复”。不要求一阶段一聊天；换聊天时提供卡目录。未明确要求后续动作时，完成当前请求就停下；明确要求“读完后整理问卷”时可以连做，BA 答复仍以用户提供为准。

## 开始与结束

开始时读取项目根目录 `AGENTS.md`、本说明、对应阶段说明和已有卡内文件。有多个候选卡且未指定目录时，请用户选定，不猜测。相关业务资料按需读取，不要求先建立项目规范。

已有卡先核对 `workflow: analysis-lite`。标识缺失或不同，先确认来源与状态含义；仅在用户明确要求迁移时才转换其他流程的卡。支持的状态和卡片结构见 [cards/README.md](cards/README.md)。

结束时把结论写进卡目录，同步 `README.md` 的状态和下一步，用简短摘要告知：改了哪些分析文档、已确认什么、还缺什么、现在需要人做什么。问卷与答复的唯一记录在卡内文件中。

## 证据与缺失信息

- 先从相关代码、配置、测试、项目文档、可读的 git 历史查现状；每条事实附路径和符号或章节，必要时带行号。git 可用时记录分支、提交和相关未提交改动；分析期间不自动同步工作区。
- 代码说明现状，业务答复决定期望。已有实现可以作为建议的理由，不能代替 BA 的产品决定。
- 将“已核实 / 未核实 / 与现有证据冲突”分开写；AI 推断单独标注。静态分析与实际复现分别记录，搜索未发现不等于确定不存在。
- 资料缺失时写清“缺什么、影响哪个判断、谁或什么资料能补齐”，继续不依赖它的部分。没有代码时只做文档分析；无法读取的截图、链接和外部系统行为均标未核实。
- 对端仓库按已提供且确实存在的路径读取；对外请求、运行项目或改变数据不属于默认分析动作。确有必要时先说明用途，由用户提供材料或明确授权。
- 技术现状问题交给代码或技术负责人，BA 问卷只保留业务意图与取舍。无法核实的技术事实留在 `01-card.md`，不能编成结论。

## 答复的边界

范围、权限、费用或数据口径、验收、不可逆的数据处置属于阻塞题，需要明确答复。低影响且可逆的细节才可标“可默认”，也必须在答复人明确接受建议后采用；沉默不算接受。

保留答复原文、答复人和日期。AI 的解读与原话分开；无权决定者的意见记录为意见，需要有权者确认。未答、含糊或冲突的关键题保持待确认。流程结束表示问答已收敛，正式确认记录只在确有原话时写入。

## 文件位置

- [cards/README.md](cards/README.md)：卡目录命名、状态和续接规则。
- [templates/card-analysis.md](templates/card-analysis.md)：读卡产物格式。
- [templates/questions.md](templates/questions.md)：问卷与逐题答复格式。
- [templates/alignment.md](templates/alignment.md)：回填后的需求结论格式。

可选的 `assets/` 只放用户提供的材料。无需建立全量规范库、独立日志或额外审批文件；可复用背景暂时放在卡的来源与事实里。
