# 需求分析精简基线

用当前工作区快照读卡，与 Dev 沿设计树讨论，再整理需求共识。需要业务判断时才提炼问题给 BA；只写卡片文档。

## 使用顺序

1. `card-intake` + 卡号与原文：按 [读卡说明](workflow/01-card-intake.md) 产出 `README.md`、`01-card.md`。
2. `clarify <卡目录>`：按 [澄清说明](workflow/02-clarify.md) 与 Dev 讨论并查证，持续维护 `02-questions.md`。原卡明确的要求直接沿用，前置不明的分支先查清；BA 问题按需整理给 Dev 审阅后自行转发。
3. `align <卡目录>`：按 [对齐说明](workflow/03-align.md) 吸收已有共识或新答复，维护 `03-alignment.md`，有缺口就继续与 Dev 讨论。可以附 Dev 补充、技术资料或 BA 回复，无需先有 BA 问卷。

三步可在同一聊天完成，澄清收敛后可直接整理结论；`align` 内发现新问题直接复用设计树继续，无需切换命令。换聊天时提供卡目录即可续接。自然语言表达同样有效；明确只读卡、只回填、暂停或直接出问卷时按当前请求处理，开放项照实保留。

## 开始与结束

开始时读取项目 `AGENTS.md`、本说明、对应阶段说明及已有卡文件。多个候选卡无法确定时请用户选定。核对 `workflow: analysis-lite`；来源不明先查明，不自动转换其他流程的卡。目录与状态见 [cards/README.md](cards/README.md)。

结束时保存当前共识、关键依据与未解问题，同步 README 的实际状态和下一步。目标、范围、关键规则与可观察 AC 已清楚，且没有影响这些判断的关键缺口时记为 `answered`；允许完全在 Dev 侧收敛，不要求 BA 答复或额外签批。一般实现细节不阻塞需求结论。

## 证据与判断

- 代码、配置、测试、文档及可读 git 历史能回答的事实由 AI 查证，附路径与符号 / 章节；区分已核实、未核实、证据冲突及 AI 推断。静态分析不等于实际复现，搜索未发现不等于不存在。
- 记录当前代码快照及相关未提交改动，不自动同步工作区。没有代码时做文档分析；外部材料不可读时注明缺失，继续不依赖它的部分。
- Dev 暂时不确定时，先共同查证、推演或请技术负责人补资料。原卡歧义、业务规则取舍或技术限制影响业务目标时才找 BA；不能把技术未知直接转交 BA。
- 原卡明确要求与既有业务决定直接引用，Dev 在既定要求内的技术决定正常记录。代码现状不能替代产品期望，新增业务取舍由相应业务负责人决定；Dev 转述按实际来源保存。
- 对端仓库按已提供且存在的路径读取。运行项目、对外请求或改变数据不属于默认分析动作；确有必要时说明用途，由用户提供材料或授权。

## 记录保持轻量

`01-card.md` 放事实与证据，`02-questions.md` 放关键讨论和待办，`03-alignment.md` 放当前有效结论。模板空节可删；相同答复来源按批记录，不逐题重复身份 / 日期，不为每轮生成完整复核报告。

Q / AC 编号与关键修订依据保留，不覆盖旧答复；发出的问题实质变化时保留所发版本，异步答复核对对应内容。明确答复直接落档，有歧义才追问；建议未被接受不写成决定，沉默不算同意。推迟项写依据、影响和后续处理，影响范围或 AC 的缺口不能仅因改称“后续项”就跳过。

## 文件位置

- [cards/README.md](cards/README.md)：目录、状态与续接规则。
- [templates/card-analysis.md](templates/card-analysis.md)：原卡、事实与影响面。
- [templates/questions.md](templates/questions.md)：Dev 澄清记录与按需 BA 问题。
- [templates/alignment.md](templates/alignment.md)：需求共识与验收标准。

`assets/` 按需保存用户材料。无需全量规范库、独立日志或额外审批文件。

方法参考：[Trellis](https://github.com/mindfold-ai/Trellis) 的证据与需求收敛，以及 [mattpocock/skills](https://github.com/mattpocock/skills) 的 grilling 设计树、按需问卷与规格整理；运行时只依赖本目录文档。
