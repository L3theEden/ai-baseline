# 02 · 整理给 BA 的问卷

输入：本卡 `01-card.md`、已有问卷和已收到的答复。产物：按 [问卷模板](../templates/questions.md) 维护 `02-questions.md`。没有读卡文档时先完成 [读卡分析](01-card-intake.md)，不要凭空生成项目事实。

默认先与用户（通常是 Dev）交互澄清，再把需要 BA 决定的部分整理成本轮问卷。每轮答复后复核新问题、依赖、冲突和验收缺口，结果持续写入同一文件。

用户明确要求直接出问卷、离线整理或跳过访谈时，可直接生成本轮问卷草稿，仍需记录待展开项和后续轮次。没有需要用户澄清的内容时也可以直接整理，说明依据，不为凑轮次制造问题。

## 筛选与组织

1. 每个问题先判断：代码、配置、文档或已有答复能否回答？能就查证、补到 `01-card.md`，不进问卷。技术资料缺失记录为技术待办，注明资料提供者；只有业务意图、规则取舍、范围和验收等需要人决定的题才进 BA 问卷。
2. 代码体现现状，不能替 BA 决定本次期望。已有实现只作为推荐的依据；卡与现有行为冲突时，明确问本次要采用哪个业务规则。
3. 范围题在最前面，再按需组织术语、规则 / 数据口径、权限 / 展示、异常处置 / 历史数据、验收。每题只问一件事；用业务语言，必要的技术证据留在读卡文档。
4. 范围尚未明确且后续问题大量依赖它时，本轮只展开范围题和独立问题，其余列入“范围确认后再问”。每个待展开项也预留唯一 Q 编号并标性质、依赖，避免关键问题在收尾时遗漏。
5. 每个正式问题注明为什么问、影响、阻塞或可默认、依赖、建议、答复位置。推荐要有依据；信息不足以推荐时说明缺什么，不编造“最佳答案”。

## 交互与逐轮复核

1. 先问范围，再问前置条件已满足的规则、场景与验收问题，同一轮将当前能问的问题编号一起列出。用户明确不知道或无权决定的题，标为待 BA 决定，不反复要求用户代答。
2. 每批答复都保留原话与来源，当前理解单列；范围、口径等关键答复有歧义时先回述理解，确认前标待澄清。有权 Dev 的明确答复注明“Dev 答”，无权决定的意见仍是建议。
3. 答复后重新检查本卡相关的范围、术语、规则 / 数据口径、权限、异常与历史数据、上下游影响和验收。已定前置题解锁哪些后续题、是否出现新场景或冲突、哪些旧结论与 AC 受影响，都要记录。技术事实先查证；已有明确依据的不重复问，不为检查项硬凑问题。
4. 仍有用户能回答且有权决定的问题就继续交互；其余整理为本轮 BA 问卷，依赖 BA 决定的细节列为待展开项。整理问卷不要求先拿到 BA 的全部答案；用户答完当前列表也不表示所有关键问题已收敛。

交互中逐轮落档，不等问完才记录。每轮说明已确认什么、新增或重开哪些 Q、哪些依赖待解除，以及下一步问谁。交互尚在进行或需要展开下一轮关键题时保持 `clarifying`。

## 答复要求

- **阻塞**：范围、权限、费用 / 数据口径、验收、不可逆数据处置等关键决定。必须能对应到明确的逐题结论；笼统“都可以 / 按建议来”不视为关键题已答。
- **可默认**：影响小且可逆的细节。答复人明确同意采用这些题的建议后才记“按建议”；未答仍是未答。
- 状态使用“待答 / 已答 / 按建议 / 待澄清 / 本期不适用”。有意见但没有决策权限的答复标“待澄清”，注明仍需谁确认。

## 审阅与后续轮次

交互中已经明确的结论带入问卷，不重新问一遍。本轮待 BA 问题整理好后，先作为草稿给用户审阅；直接文档式也保留这一步。用户能够且有权回答的题注明“Dev 答”，其余按收件人分组。收件人未知就标待指定，不自动找人或发送消息。问卷可在审阅前保存；整理出本轮待 BA 问卷后，`stage` 记为 `awaiting-ba`，进度文字注明实际是“待用户审阅后转发”还是“等待答复”，不虚构审阅或发送记录。如果仅精简措辞或排版，未改变已有决议、建议与验收，也没有新增问题，则保留原状态。

每轮说明本次要拿到哪些关键结论。原 Q 编号不变，新题从已有最大编号递增；已答问题保留，重开问题保留原答复和原因，改动建议后原先“按建议”的答复也要重新核对。已被范围决定排除的题标“本期不适用”并引用依据。

末尾记录需求合理性或价值上的疑点，有疑点就附证据、影响和更小替代方案；没有则简述理由。验收草稿写可观察的 Given / When / Then，不能把未答问题的推荐当成已确认验收。

若已有 `03-alignment.md`，同步其开放问题和状态，不能保留过时的“已收敛”结论；已有确认记录按需标明受本轮变更影响。

收尾给出问卷路径、最需要 BA 明确的题和用户接下来要做的事。收到答复后按 [回填说明](03-align.md) 处理；已有明确授权时可在同一聊天接着回填。
