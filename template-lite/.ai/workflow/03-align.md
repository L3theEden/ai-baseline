# 03 · 回填答复与整理结论

输入：本卡文档、用户提供的 BA / Dev 答复及其来源。产物：回填 `02-questions.md`，按 [结论模板](../templates/alignment.md) 创建或更新 `03-alignment.md`，同步 `README.md`。没有问卷或问题无法对应时，先识别对应关系；无法确定的答复记录为“待映射”，请用户指出对应题，不硬凑决议。

允许部分答复，允许多轮补充。记录答复就是本阶段的工作，不额外要求一次“批准回填”。

没有新增答复，但原卡与已有明确来源已覆盖全部关键决定时，也可据此检查收敛，记录所用依据，不为凑问答虚构 BA 答复。

## 默认连续澄清与回填

用户启动 `align` 或明确请求回填答复后，本卡的回填、逐轮复核、设计树追问与结论更新属于同一个需求问答循环。发现新问题时直接复用 [问卷说明](02-clarify.md)，不要求重新输入 `clarify`，也不自行调用阶段 skill。同一聊天直接回答即可继续；换聊天用 `align <卡目录>` 续接，包括 `stage: clarifying` 的对齐中澄清轮次。

每轮一起提出前置条件已满足、用户能够且有权回答的问题，附依据与建议，等待答复后重算依赖。用户不知道或无权决定的题，整理为本轮 BA 问卷，交用户审阅、由用户转发，再等待有权者答复；不反复要求用户代答。用户明确要求只回填、暂停追问或直接整理问卷时按其要求处理，未答、冲突和待展开项照实保留，不因此记为 `answered`。

## 回填

1. 在各 Q 下记录原话、答复人、实际答复日期和来源（如用户转述、附件标题）。未提供的人名或日期写“未提供”，不把转述人自动认成 BA，也不补造日期。
   - 先核对对应 Q、轮次 / 题干与建议版本；未给编号但对应关系唯一明确时可映射并说明依据。存在多种对应，或旧版答复无法覆盖新版改动时，保留为待映射 / 待澄清，只追问受影响部分，不覆盖记录，也不阻塞其他明确答复的回填。
2. 保留原答复，再单列“当前理解 / 决议”。只有能明确对应到该题且由有权者作出的答复才记“已答”；建议、含糊表达或冲突记“待澄清”。阻塞题遇到“按建议来”的笼统回复仍需明确结论；可默认题明确接受建议后记“按建议”，并保存当时接受的建议内容。
3. 对含糊答复，先写清可能的两种理解与影响，再提出最少必要的追问。部分答复先落档，不能因为一题未答就丢掉其他明确结论。
4. 新答复与旧答复冲突时，保留两者及来源。只有明确是在修订原决定且有相应权限时，才将旧结论标“已被取代”；否则保持冲突待确认。建议变化、范围变化或验收变化时核对所有受影响的 Q 和 AC；技术前提变化或与旧证据冲突时重新查证受影响事实，技术现状与产品期望分开记录。

## 每批答复后的复核

按 [问卷说明](02-clarify.md) 的“交互与逐轮复核”主动检查依赖、新场景、规则冲突和验收缺口，不只核对已有题是否填满。前置明确后，仍在范围内的待展开题和待细化领域必须继续展开；已排除的标“本期不适用”并引用依据。

新问题进入同一份问卷，Q 编号从已有最大编号递增；重开旧题时保留原答复及原因。把受影响的既有决议和 AC 标清。需要展开新一轮时，先保存本轮明确答复和结论草稿，再直接按设计树追问；收到答复后继续回填、复核和更新结论，无需重新输入命令。

每批答复后，把以下“本轮复核结果”简要写入问卷的轮次记录，在回复中呈现，并在结论中引用：

- **依赖展开**：哪些已答 Q 或已查明事实解锁哪些后续 Q，哪些待细化领域已可展开，哪些移出范围、哪些仍被前置问题或资料阻塞。
- **场景与冲突**：根据本卡相关的正常流程、权限、异常、历史数据与上下游场景推演答复的后果，说明检查了哪些边界、发现什么缺口，并核对原卡、旧决议、术语和已核实技术约束。不相关项可说明不适用，不为凑数增加问题。
- **验收覆盖**：新增或变化的范围、规则与场景对应哪些 AC；受未答题或冲突影响的标为草稿，缺少可观察验收结果时形成追问。宣称收敛前，再交叉核对整卡的范围、业务规则与 AC，检查是否还有从未列入问卷的关键取舍。
- **本轮判断**：继续追问（列出当前可问的 Q）、等待有权者答复或缺失资料（列出 Q / 缺口与影响），或关键问答已收敛（说明没有留下关键开放项的依据）。不同类型的开放项可以并存；能继续处理的部分先处理。

不能只写“已检查，无新问题”或勾选完成。没有新问题可以收敛，但必须有复核依据；当前没有可立即提问的问题时，仍要核对被资料阻塞的题和待细化领域，有关键题、关键冲突或影响范围与验收的缺口时不能收敛。新增问题按问卷说明的目标与边界筛选，范围外建议不自动变成本卡阻塞项。

## 整理当前结论

- 目标、范围内外、术语、业务规则与数据口径：每条关键结论引用 Q 编号或明确的卡片原文 / 确认来源。没有依据的内容标为建议或开放问题。
- 决议：记录 Q 编号、决定、答复方式（BA 答 / 有权 Dev 答 / 明确接受建议）、理由与来源。用户仅转述答复时按原答复来源记，不据此虚构其权限。
- 验收标准：用编号稳定的 `AC-1`、`AC-2` 等描述 Given / When / Then 可观察结果，标“已确认依据”或“草稿待确认”。明确的原卡标准也可作为依据；涉及未答关键题时只能写草稿。
- 疑点处置：需求价值质疑被采纳、否决还是未处理，保留决定与理由。关键疑点没有处置结论时仍属于开放问题。
- 开放问题与推迟项：分清未答关键题、待展开关键题、待细化领域、待澄清答复、技术资料缺口和可推迟细节，写清影响、负责人或资料来源。业务题推迟须有有权者的明确决定；技术未知项由 Dev 评估可推迟并记录依据、影响与后续处理，会改变本期范围或验收的缺口仍阻塞收敛。

## 决定状态与下一步

按 [状态规则](../cards/README.md) 判断：

- 只是部分答复，仍等关键答复：`awaiting-ba`。
- 正在设计树追问、审阅草稿或需展开下一轮关键题：`clarifying`。直接按 [问卷说明](02-clarify.md) 继续当前可回答的问题；待 BA 问卷整理好后按其审阅规则转为 `awaiting-ba`。状态变化不要求用户切换命令。
- 用户目标与可观察的成功表现明确，所有阻塞题均有有权者的明确答复，关键范围、口径、验收已收敛，没有未处理关键疑点、待展开关键题或影响范围与 AC 的待细化领域，影响关键判断的技术缺口已解决：`answered`。推迟项满足上述条件，不能仅因标为“低影响”就视为可推迟。

记为 `answered` 前，按 Trellis 的收敛整理思路重读一次结论文档：每题只呈现一个当前有效决议，合并重复事实，移除已解决的开放项；原话与修订历史保留在问卷中并引用。不丢 Q / AC 编号、证据、决议来源和推迟项，不额外增加批准步骤。

汇报已确认的关键结论、明确按建议处理的题、本轮复核结果和开放项。当前用户能够且有权回答的直接追问；需要 BA 决策的给出待审阅问卷；缺资料的说明影响与来源。保持验收草稿与已确认部分的区别；生成结论文档不等于问答已收敛，仅“有答复”也不等于“所有结论已正式批准”。如用户提供了明确确认原话，可在结论中记确认人、日期、原话及适用版本；后续实质变更则注明原确认不覆盖这些变更。

`answered` 是本流程终点。到此保留分析文档，不创建后续阶段产物。
