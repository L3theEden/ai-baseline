# 03 · 整理共识与继续对齐

把原卡依据、Dev 讨论、查证结果及按需取得的 BA 答复整理成当前需求结论。按 [结论模板](../templates/alignment.md) 维护 `03-alignment.md`，讨论留在 `02-questions.md`，进度写入 `README.md`。无需先有 BA 问卷或 BA 回复；已有依据足够时可直接整理。

## 接续讨论

`align` 与 [clarify](02-clarify.md) 共用同一个设计树循环：吸收新信息 → 核对受影响的结论与 AC → 继续与 Dev 讨论当前可展开的问题 → 更新共识。用户直接回答即可，不必切回 `clarify` 或重复输入 `align`；换聊天时提供卡目录续接。

Dev 补充事实、解释流程、作出职责内的技术决定时，直接按其性质记录；原卡已明确且没有冲突的要求直接沿用。不能仅因答复来自 Dev 就把已有结论重开为待 BA 审批。未知事实先查证；需要业务判断的部分按 clarify 的规则提炼给 BA。用户要求只回填或暂停时保存进度、保留开放项。

## 吸收答复与复核

1. **记录有效信息。** 在 `02-questions.md` 保存关键原话或准确摘要、来源及当前理解，同一批来源可合并记录，相关结论引用对应来源，跨轮不覆盖。用户转述不等于本人作出决定，不补造姓名、日期或 BA 确认。没有 Q 编号但含义明确时直接归入相关结论；只有对应关系含糊才追问。
2. **处理差异。** 明确接受且对象唯一的建议可记为结论；含糊、冲突或超出答复者职责的业务意见保持待确认。结论被修订时保留旧结论与原因；异步答复核对其对应的题干 / 建议，旧答复只影响能覆盖的部分。清楚的答复不再追加确认手续。
3. **重算设计树。** 检查新信息解锁哪些分支、哪些场景不再适用，以及是否影响原卡、关键异常路径和 AC。技术未知先与 Dev 查证和推演，不能自动转给 BA。只记录实际变化、关键依据与下一步，不固定输出多栏复核报告。

局部缺口不阻塞其他分支；需要继续讨论时先保存明确结论，再直接提出本轮可讨论的问题。Q / AC 编号保持稳定，实质变化核对受影响的结论，不重复抄写讨论记录。

## 整理结论

- **需求与范围**：为谁解决什么问题、本期包含与排除什么。引用原卡或讨论依据，不为已有明确要求新建确认题。
- **关键共识**：必要的术语、业务规则及影响需求的技术约束，注明原卡依据 / Dev 决定 / BA 决定 / 待确认。只保留当前有效结论，历史指向澄清记录。
- **验收标准**：沿用稳定的 `AC-1` 等编号，用 Given / When / Then 写可观察结果。依据原卡或已有决定即可；受到未解问题影响的部分标草稿，忠实改写已有 AC 不需要再次交 BA 批准。
- **开放项与后续项**：写清问题、影响、谁处理、何时重访。影响范围、关键规则或验收的缺口仍须解决；一般实现细节可留给后续开发。业务取舍延期须有相应业务负责人的决定，技术后续项由 Dev 评估并说明不影响需求收敛的依据。有价值疑点时记录处置及理由。

## 状态与结束

按 [状态规则](../cards/README.md) 记录实际进度：

- 仍在与 Dev 讨论、查证或展开关键分支：`clarifying`，即使同时有 BA 待答项也可以继续独立工作。
- 本轮业务问题已经 Dev 审阅，确实等待 BA 转发 / 答复，当前无可继续的 Dev 讨论：`awaiting-ba`。仅收到部分 Dev 答复或生成文档不进入这个状态。
- 目标、范围、关键规则与可观察 AC 已清楚，没有关键冲突、待展开分支或影响判断的技术缺口：`answered`。原卡、证据与 Dev 共识足够时，无需经过 BA 问卷即可完成。

结束前核对范围与 AC 的对应关系、待查项和尚未展开的分支，简述为何已经足够；不要以“本轮列表答满”代替收敛。无需穷举未来需求，也不要求实现方案全部定稿。没有关键缺口时直接保存结论并结束，不另加正式签批；若用户确实提供确认记录，按原话保存即可。

汇报当前共识、剩余关键问题及下一步。`answered` 是精简版终点；后续新信息使关键结论失效时，保留修订依据并重开相应未完成状态。
