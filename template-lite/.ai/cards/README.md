# 卡目录与状态

每张卡一个目录：`.ai/cards/<feat|fix|unknown>-<卡号>-<slug>/`。slug 从标题取少量英文词，使用 kebab-case；类型无法判断时用 `unknown`，并在读卡文档注明。

卡号来自用户。没有卡号时请用户给出原卡号，或明确指定一个本地分析标识，AI 不自编业务卡号。标识原文保存在 frontmatter；目录名里的路径分隔符等特殊字符转为连字符。

## 按进度生成文件

- `README.md`：卡片标识、状态、一段当前进度和下一步。
- `01-card.md`：原始卡内容、证据、影响面和缺失信息。
- `02-questions.md`：Dev 澄清记录、关键依据、待查 / 待展开项，以及按需出现的 BA 问题。
- `03-alignment.md`：当前需求结论、决议、验收标准与开放项。
- `assets/`：可选，用户提供的截图或样例。

多个仓库涉及同一卡时，选一个分析主仓库存文档，其余只作为资料来源记录路径；不要求在每个仓库重复建卡。

## `README.md` 起始格式

```yaml
---
id: "<用户提供的卡号或本地分析标识>"
workflow: analysis-lite
type: feat
title: "<卡标题>"
stage: intake
created: "<YYYY-MM-DD>"
updated: "<YYYY-MM-DD>"
---
```

frontmatter 后写一段话：本卡现在确认到哪里、尚缺哪些关键信息、下一步是什么。日期用实际日期；卡原文与答复日期不能用当前日期补造。frontmatter 字符串按 YAML 转义。

## 状态规则

- `intake`：读卡进行中，允许继续 `card-intake`。
- `clarifying`：与 Dev 讨论、查证、审阅业务问题草稿或展开关键分支。可用 `clarify`；也可用 `align` 吸收已有共识或新信息并继续讨论，无需先有 BA 问卷。
- `awaiting-ba`：本轮确有业务问题且已由 Dev 审阅，正在等待转发 / BA 答复，当前无可继续的 Dev 讨论。README 注明实际是待转发还是等答复，不虚构发送记录；仅生成文档、等技术资料或收到部分 Dev 答复不进入此状态。
- `answered`：目标、范围、关键规则与可观察 AC 已清楚且有依据，没有关键冲突、待展开分支或影响判断的技术缺口。一般实现细节可由 Dev 说明依据后留后续开发；业务延期或移出范围须有相应业务负责人的决定。无需经过 BA 问卷或额外签批，至此分析结束。

澄清收敛后可直接整理结论并进入 `answered`，不要求再输入 `align`。等待 BA 时仍可处理独立分支；恢复 Dev 讨论或查证就记为 `clarifying`，同时在 README 保留 BA 待答项。收到部分答复后按剩余工作的性质判断状态，不一律转为 `awaiting-ba`。

`align` 可在讨论、查证与整理结论之间继续，不因状态变化要求切换命令。新信息使已收敛的关键结论失效时重开相应状态，保留旧结论与修订原因。新增事实可用 `card-intake`，重新读卡不清空下游记录或无条件重置状态。

已有同卡目录时先读取再追加，禁止重建覆盖。跨轮 Q 编号唯一且不复用；移出范围的题标“本期不适用”，保留其原文、答复和变更原因。历史结论被新答复取代时保留原记录与来源。

`workflow: analysis-lite` 标识本流程。缺少该字段或字段值不同的已有卡，先核对来源；确定是本精简版卡片后可补标，其他流程的卡仅在用户明确要求时迁移。这里只使用上述四个状态，读到其他状态时不静默映射。无需在答复收敛时自动移动或删除卡目录。
