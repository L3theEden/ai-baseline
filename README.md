# AI 开发基线

把需求理解、业务决议、验收标准与项目知识写进仓库，让 AI 协作从已有事实和明确范围开始。

这是一套纯 Markdown 模板，包含流程手册、卡片文档模板和 AI 命令入口。按团队的 BA → Dev → QA 流程组织工作，可供读取 `AGENTS.md` / `CLAUDE.md` 的 AI 编码工具使用。流程执行依赖工具读取并遵守文档，关键业务决定仍由有权者确认。

## 选择适合的版本

- **[精简版 `template-lite/`](template-lite/)**：适合读卡、与 Dev 沿设计树澄清并整理需求共识，业务判断问题按需提给 BA。按卡查证项目事实，只维护本卡文档，不必先建立全量规范库。关键问题收敛后记为 `answered`，分析结束。
- **[完整版 `template/`](template/)**：包含完整七阶段和轻量维护路径。新需求与复杂变化继续完成开发计划、开发与评审、DC、QA 和结卡；预期明确、低风险的小修复可用 `maintain`。两条路径共用项目规范、上下游上下文、决策与日志。

两个版本共用 `.ai/` 和阶段命令名，**同一业务仓库选择一套流程**。已有完整版时也可只使用前三阶段；切换成精简版时，按[精简版使用指南](03-精简版使用指南.md)核对并迁移卡片状态。

## 快速接入

先在业务仓库之外下载模板库，将 `/path/to/ai-baseline` 替换为实际保存路径：

```bash
git clone https://github.com/L3theEden/ai-baseline.git /path/to/ai-baseline
```

进入**目标业务仓库根目录**。仓库尚无同名 AI 配置时，选择下面一种模板复制；命令会包含隐藏目录。

精简版：

```bash
cp -R /path/to/ai-baseline/template-lite/. .
```

完整版：

```bash
cp -R /path/to/ai-baseline/template/. .
```

已有 `AGENTS.md`、`CLAUDE.md`、`.ai/` 或同名 skills 时，先合并并核对现有内容，按下文的[升级说明](#已有项目怎么升级)处理。

复制后，精简版可直接从一张卡开始；完整版先按[推广指南](02-推广指南.md)登记模板来源提交与项目适配，填写项目入口和 `spec/`、`context/` 中的事实。占位骨架与虚构示例不能当成项目现状。

## 从第一张卡开始

以下内容输入到 AI 聊天中。Claude Code 可使用对应的 `/<命令>`，其他工具可直接说出命令名或流程文件路径。

**1. 读卡并查证事实。** 卡号和内容来自实际需求；AI 返回卡目录路径，后续都使用这个路径。

```text
card-intake

卡号：<真实卡号>
标题：<卡标题>
卡内容：<BA 原文>
验收标准：<原文；没有就写未提供>
相关材料：<已有文档、样例或对端仓库路径>
```

**2. 与 Dev 沿设计树讨论。**

```text
clarify <卡目录>
```

AI 先查事实，沿用明确的原卡要求，再与 Dev 讨论前置已明确的问题并给出建议。Dev 拿捏不准的先查证、推演或补资料；需要业务判断时才提炼给 BA，经 Dev 审阅后自行转发。可以完全在 Dev 侧收敛，无需生成 BA 问卷。

**3. 整理共识，有缺口继续讨论。**

```text
align <卡目录>

补充：<可选：Dev 答复、查证资料或 BA 回复；有转述时注明实际来源>
```

`align` 从原卡、证据和已有 Dev 共识整理结论，不以 BA 回复为前提。同一聊天直接回答或补充资料即可继续，**无需切回 `clarify` 或重复输入 `align`**。换聊天时提供卡目录续接；精简版的 clarify 收敛后可直接完成结论整理。

需要直接出问卷时，可以说“跳过交互，整理本轮 BA 问卷草稿”；只想保存答复时，可以说“只回填，先不追问”。未解决的问题会保留。

精简版在关键问答全部收敛后记为 `answered`，结束分析；完整版的完整流程在关键问题收敛后呈现最终摘要，收到后续消息中的明确批准，才放行 `dev-plan`。开发计划另有设计确认和拆解确认，拆解确认后才可开始实现。

## clarify 和 align 的分工

- **`clarify`：与 Dev 把需求讨论清楚。** 从已有依据出发，沿设计树发现缺口、查证事实、讨论流程与关键取舍；需要业务判断时再提炼给 BA。
- **`align`：把共识整理为做什么、如何验收。** 吸收原卡、Dev 讨论、技术资料和按需取得的 BA 答复，整理当前结论；有缺口就继续同一个设计树循环。

每轮简述新增共识、对相关场景与 AC 的影响、下一步即可，不填写固定复核报告。明确答复直接记录，有歧义才追问；原卡已经写明且没有冲突的要求无需重新向 BA 确认。

**收敛看需求是否清楚、关键缺口是否解决。** 仍需核对被资料阻塞的分支、关键冲突及验收缺口；技术资料只阻塞相关分支，其余继续。一般实现细节留给后续开发，额外能力留作建议，不穷举本卡范围外的设计。

保留问题编号、关键来源与实质修订依据；同批来源集中记录，已转发问题变更时保留所发版本，异步答复核对对应内容。技术后续项由 Dev 评估，业务取舍延期由相应业务负责人决定；影响本期范围或验收的缺口不能靠改称后续项跳过。新信息影响已收敛结论时如实重开。

## 流程与产物

精简版：`读卡 → 澄清 ↔ 对齐 → answered`。

完整版的完整流程：`读卡 → 澄清 ↔ 对齐 → 开发计划 → 开发与评审 → DC → QA / 结卡`。

完整版的轻量维护：`核实条件与授权 → 修复 → 验证与评审 → 按授权交付 / 归档`。

完整流程默认分阶段使用会话，02 澄清与 03 对齐可以连续问答，后续阶段仍由用户显式触发；轻量维护可在一个窗口内连续完成。完整命令、状态和门禁见[流程总览](template/.ai/workflow/overview.md)。

每张卡在 `.ai/cards/` 下有独立目录。完整流程随阶段生成文件，轻量只维护卡 README 和 `maintenance.md`；以下完整卡目录名为虚构示例：

```text
.ai/cards/feat-DEMO-123-task-status-filter/
├── README.md          # 卡片标识、状态、当前进度与下一步
├── 01-card.md         # 卡原文、事实核实、影响范围与缺失信息
├── 02-questions.md    # Dev 澄清记录、待查与待展开项、按需 BA 问题
└── 03-alignment.md    # 当前需求结论、范围、决议、验收与开放项
```

完整流程后续增加开发计划、`tasks/` 子任务单、开发与评审记录、DC 文档。04 列文档影响，05 随实现更新项目知识并评审，06 核对验证范围，结卡时提炼经验和归档。换工具或换会话时，从卡目录续接。

项目规范与共享契约维护现行结论，完整卡未来方案保存在已批准的 03/04，轻量目标与本次授权记录在 `maintenance.md`，历史保留证据指针。关键事实注明来源与核实范围，分别记录代码已实现、已部署和环境已验证；具体见[项目文档维护](template/.ai/workflow/documentation.md)。

完整版按[任务触发条件](template/.ai/spec/index.md#开发前按任务类型必读)读取相关规范章节，并说明用途；必要上下文不受三份规范的数量限制。卡 README 保留[当前恢复摘要](template/.ai/cards/README.md#当前恢复摘要)，历史通过阶段记录与[日志索引](template/.ai/journal/README.md#轻量索引与检索)追溯。日志同月续卷，经验记录待处理 / 已沉淀 / 无需沉淀及去向。文档保留语义与主来源，使用现有工具人工核对路径、章节、镜像及行为证据。

完整版随附[最小实现与修复原则](template/.ai/workflow/implementation-principles.md)，供完整流程与轻量维护共用：先核对必要性、复用和已有能力；修 bug 前核查调用链与相关入口；有意简化时写清当前依据、已知上限和重新评估条件。通用规则可直接引用，项目约定仍须填写；已实施的持续限制写回 `spec/legacy.md`，保留历史依据。

## 结卡后的轻量维护

已完成的卡保留决议、验收和验证证据。后续局部修复可以引用原卡，另建关联的维护记录；原卡未结项且属于原范围的缺陷，继续原卡回流。

```text
maintain <具体问题、预期结果和可选的原卡链接>
```

AI 先核实轻量条件。用户已明确要求修复且条件满足时，记录实现授权并继续，不重复要求完整设计确认；只要求评估时只评估。提交和推送按各自的已有授权执行。没有外部卡号时，可按项目规定使用明确标记的本地维护标识。

**可轻量**：恢复既定行为或纠正文档 / 展示，单仓库、局部、可恢复、能验证且符合项目门禁。**须升级**：业务规则 / 范围变化，或涉及权限、关键计算、数据迁移、共享契约、并发、跨仓库及其他高风险或未查清的影响。升级保留代码与证据，在同一卡目录切入缺失的完整阶段，不补造批准。细则见 [轻量维护手册](template/.ai/workflow/maintenance.md)。

轻量维护属于完整版；`template-lite/` 仍只覆盖需求分析。旧卡缺少 `workflow` 字段时继续按完整流程处理，已有完整卡不自动降级。

## 已有项目怎么升级

升级模板时，先查看差异，再按项目实际内容合并：

1. 比较并合并所选版本的 `.ai/workflow/`、`.ai/templates/` 和 `.ai/cards/README.md`，保持流程与产物格式一致，保留项目适配。
2. 合并 `AGENTS.md`、`CLAUDE.md`、`.ai/README.md` 的入口规则，保留已填写的项目信息；核对 `.agents/skills/` 与 `.claude/skills/` 是否仍指向对应流程。
3. 保留实际卡片、项目规范、上下游上下文、决策和日志，尤其是 `.ai/cards/<实际卡>/`、`.ai/spec/`、`.ai/context/`、`.ai/decisions/`、`.ai/journal/` 中的项目内容。
4. 已有卡用 `align <卡目录>` 续接，保留原 Q 编号、关键答复与修订依据。旧 BA 问卷可沿用文件名，先区分已有依据、Dev 讨论、技术待查和确需业务判断的题，再更新状态；不删除历史或批量当作已答，也不因原卡已有要求缺少 BA 重复确认就持续阻塞。

**完整版**在 `.ai/README.md` 登记来源仓库、模板目录、来源提交、最后完整同步日期及项目适配。升级按[来源与升级协议](template/.ai/workflow/baseline-upgrade.md)比较“旧模板、当前项目、新模板”；旧来源不明时逐文件核对并保留项目内容，部分升级单独记录，完成后才更新来源版本。修改本模板库不自动升级任何业务项目。

## 业务资料与对外分享

本仓库用于维护通用模板，实际业务资料留在目标业务仓库。文档中的任务管理场景、`DEMO-*` 卡号和示例代码路径均为虚构示例。

卡片、日志、接口样例和项目规范可能包含内部信息。对外分享前同时检查文件与 Git 历史，用虚构示例替代真实业务数据，并移除内部地址、个人信息与凭证。
