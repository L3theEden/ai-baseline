# 07 · 交 QA 与结卡（QA Handoff）

QA 依据 `03-alignment.md` 的 AC 与 `06-desk-check.md` 的演示脚本测试。本阶段处理完整流程卡的 QA 反馈、关闭卡、提炼经验。轻量维护按 [维护协议](maintenance.md) 在维护记录中保留项目要求的 QA / 验收结果。日常事实和契约变化已在开发阶段按 [项目文档维护](documentation.md) 回写，本阶段复核与收尾。

## QA 反馈处理

- **通过**：在 `06-desk-check.md` 的"QA 结果"段逐条 AC 回填通过 / 日期 / 测试人。
- **缺陷，属于本卡 AC 范围**：`stage` 回到 `in-dev`，在 `05-dev-log.md` 追加"QA 修复轮次"，按需新增修复子任务单（编号接着排），走 05 的派发与评审，修复后重新走 06 的对应 AC。
- **缺陷源于设计**：`stage` 回到 `planning`，在新窗口修改开发计划并重新确认。
- **缺陷，超出本卡 AC**：另建关联的修复记录，按 [轻量条件](maintenance.md#可以走轻量的条件) 判断可否维护，否则新开完整 `fix` 卡；原卡不因范围外缺陷自动阻塞，范围内问题仍须完成验收。
- **QA 质疑 AC 本身**：回到 03 与 BA 重新对齐，不在开发阶段私下改 AC。

原卡已经 `done` 后发现新问题，保留原卡历史并建关联记录，再按维护条件分流；不覆盖原来的批准和验收。

## 结卡清单（全部 AC 通过后）

1. **复核回写并提炼。** 先核对 04 的文档清单及 QA 修复新增的影响，确认现行说明与最终实现、验证范围一致，遗漏立即补齐。再问自己："这张卡教会了什么，未来的 AI 或同事不知道会再踩一次？"逐项判断并落笔：
   - 新约定或新配方 → `spec/conventions.md`
   - 对齐文档"术语"一节里新定下的词 → `spec/domain.md` 的术语表
   - 新坑、临时方案、被迫的妥协 → `spec/legacy.md`（写现象 / 原因 / 影响 / 处理建议 / 证据 / 状态）
   - 难回头且有真实取舍的决定 → `decisions/adr/`（极简格式，见该目录 README）
   - 被否决的方向 → `decisions/rejected/`
   - 契约与上下游的最终验证结果 → 补 `context/api-contract.md` / `context/upstream-downstream.md` 的证据与适用范围，复核主来源与镜像
   - 新的"改 X 前要想到 Y" → `spec/guides.md`
   结论是"没有要写的"也可以，但要走一遍判断并在 journal 里写明。`05-dev-log.md` 的偏差段记录了计划与实际的差异，是最重要的回写来源。
2. **bug 卡加做根因分析。** 根因五类：缺规范 / 跨层契约不清 / 改一处漏一处 / 测试盲区 / 隐含假设。写明预防机制（文档、类型、测试、检查清单）并落实到对应文件。
3. **写 journal。** 按 `journal/README.md` 追加本卡条目（模板 `templates/journal-entry.md`），逐项记录“已回写到”的状态与去向。必需回写须已完成；额外经验的待处理项写明缺口与后续安排，留给月度复查。
4. **归档。** `stage: done`，更新当前恢复摘要；卡目录移到 `.ai/cards/archive/YYYY-MM/`，链接仓库的同名目录一并移动，并按 `cards/README.md` 修正受影响的引用。
5. **提交。** 文档改动与代码分开提交，信息带卡号。

## 完成标准

- QA 结果已回填，`stage: done`，目录已归档。
- 本卡必需的 spec / context / decisions 回写已完成或已明确无需回写；额外经验的去向在 journal 中逐项记录。
- 04 文档清单与 QA 修复影响已核对，现行说明、历史指针和验证范围一致；部署状态以证据为准，不因结卡自动标为已部署。
