# 06 · DC（Desk Check）

产出 `06-desk-check.md`（模板 `.ai/templates/desk-check.md`），供 Dev 向 BA 与 QA 演示"做了什么、证据是什么、上线要注意什么"。DC 的读者是 BA 和 QA，所以用业务语言，证据放前面。

## 步骤

1. **变更摘要。** 用最小的视图讲清改动：调用树、状态机、文件树或 diff 草图，选一种最能说明本卡的形式；一两段话即可。
2. **逐条 AC 演示脚本。** 对 `03-alignment.md` 的每条 AC：
   - 演示步骤（在哪个环境、用什么数据、点什么或调什么接口）。
   - 预期结果。
   - 证据：按可信度排序。截图或录屏最好；测试名与输出次之；日志片段再次。证据必须来自真实执行，不能是"预计会通过"。证据从 `05-dev-log.md` 的"自测证据"和各子任务单的执行、评审记录里取。
   - 状态：通过 / 部分 / 未做（写原因）。
3. **影响面。** 实际改动的模块、接口、表、配置键；与 `01-card.md` 初判、`04-dev-plan.md` 设计的差异及原因。
4. **部署前置。** 新迁移脚本版本号；新 ConfigMap / Secret 键（必须在部署平台的测试与生产命名空间预建，CI 只做只读校验）；是否需要先发后端再发前端；是否需要手动触发同步或回填。
5. **合并风险。** 单向门还是双向门（回滚是否容易）；爆炸半径（影响哪些用户、哪些上下游、哪些定时任务）；回滚步骤。
6. **未覆盖与已知限制。** 哪些边界没测、哪些依赖测试环境无法验证、哪些留到后续卡。
7. **QA 关注点与数据准备。** 建议 QA 重点看的场景、需要的测试账号 / 测试数据 / 功能配置、灰度白名单设置。
8. **QA 结果回填段。** 留空，交 QA 阶段填。

## 门禁

- DC 会议前：本地门禁绿，`06-desk-check.md` 每条 AC 都有证据。
- DC 会议通过：`stage: in-qa`，按 `session-protocol.md` 收尾（下一个窗口：`qa-handoff`）。未通过：记录意见，回到 05（`stage: in-dev`）；是设计问题回到 04（`stage: planning`）。

## 常见错误

- 证据写"已自测通过"四个字。要有测试名、输出或截图。
- 漏掉配置预建。上线时 Pod 起不来往往是这个原因，见 `spec/config-and-deploy.md`。
- 把 DC 写成技术流水账。BA 只关心 AC 是否达成，QA 只关心怎么测。
