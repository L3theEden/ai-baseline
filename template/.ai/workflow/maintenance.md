# 轻量维护（Maintain）

处理预期明确、影响可核实的局部修复与文档 / 展示纠正。入口是 `maintain <问题描述或维护卡目录>`，或用户明确要求“按轻量维护修复……”。先核实适用条件，再在已有授权内完成实现、验证和评审；用户只要求评估时只做评估。详细记录集中在卡内 `maintenance.md`，模板见 [维护记录](../templates/maintenance.md)。

## 先选对路径

- **原卡尚未结项，缺陷属于原卡验收范围**：继续原卡既定路径。完整卡按 [完整流程回流](overview.md#卡状态机) 返回开发、计划或对齐；维护卡继续本次记录并核对是否需要升级，不另开卡绕过原卡尚未完成的验收。
- **原卡已结项 / 归档、原卡范围外的独立问题，或独立维护已有行为**：可以评估轻量路径。新建关联原卡的维护记录，保留旧卡的结论与批准；没有原卡时引用现行规范、测试和用户请求。
- **完整流程中的“轻量卡”**：只是缩减 04 的设计内容，仍属于完整流程；不等同于本路径。已有完整卡不通过修改 `workflow` 降级。

## 可以走轻量的条件

以下条件须全部有依据；文件少、只改一行、任务名叫 bug 或要求尽快处理都不能代替判断。

1. **预期已明确。** 属于恢复已约定行为，或不改变业务含义的文档 / 展示纠正；已有 AC、现行规则、测试和明确用户请求之间没有待决定的冲突，不新增功能或重定业务规则。
2. **影响可界定。** 单仓库、局部改动，相关调用与回归范围能查清；不需要跨仓库配合、重新进行架构设计或扩展任务范围。
3. **风险低且可恢复。** 不触及下节的高风险变化；能说明代码回退或文件恢复方式，不依赖不可逆操作修复问题。
4. **能够验证。** 行为缺陷有复现依据和可执行的回归检查；文档 / 展示修正有对应的链接、渲染或人工检查方法。不为纯文字改动强加无关测试。
5. **项目要求可以满足。** 项目规定的构建、测试、评审、QA 和发布条件仍可落实。轻量路径不免除项目已有的交付要求。

先只读核实必要事实，记录每项依据。影响分流的事实仍未知时，不能假定满足条件；无法排除升级条件则进入完整流程。技术事实自己查，只把仍需有权者决定的预期、范围与取舍交给用户。

## 必须升级的情况

命中任一项即停止依赖轻量授权的实现，并按下文升级；不以“顺手一起改”扩展范围：

- 新增功能、改变产品规则 / AC，或现有预期存在实质冲突，需要业务决定。
- 改变认证授权、安全边界、敏感数据处理，或金额、计费等关键业务计算逻辑。
- 新增 / 修改表结构、数据迁移、批量回填 / 删除 / 修复数据，或其他不可逆操作。
- 改变共享接口的字段、枚举、错误语义或兼容规则；需要其他仓库或外部系统协调交付。
- 改变事务、并发、锁、幂等、状态流转，或定时 / 异步任务的执行机制与外部写入行为。
- 引入依赖或外部集成，调整架构、部署权限、发布机制、关键配置默认值；需要扩大授权范围或无法证明局部修复足够。

若只是测试环境暂时不可用，而适用条件已核实，保留当前状态和验证阻塞，不为等待环境重走需求流程，也不能宣告完成。紧急程度不改变分流条件。

## 记录、状态与授权

- 在 `.ai/cards/fix-<标识>-<slug>/` 保存 `README.md` 和 `maintenance.md`。有外部卡号时沿用；没有时可生成 `local-YYYYMMDD-NN` 本地维护标识并注明来源，NN 为同日序号，核对活动与归档卡避免重名，不冒充 BA 或工单系统编号。项目若强制外部工单仍遵守；其余情况不额外要求先去开 BA 卡。
- README 写 `workflow: maintenance`，`stage: intake`，按 [当前恢复摘要](../cards/README.md#当前恢复摘要) 维护入口；原卡放入 `links`。`workflow` 缺省表示 `full`，不能将旧卡自动视为轻量。
- 状态为 `intake → in-dev → done`。`intake` 只核实条件和授权；全部满足且实现已授权才进入 `in-dev`。验证、评审或交付阻塞时保留 `in-dev`，阻塞写入 README；满足完成条件才 `done`。状态只以 README 为准。
- **实现授权可以来自用户已有的明确修复请求。** 将请求人、日期、原话、具体目标与范围记入维护记录，先呈现简短分流和改动边界，然后在原授权内继续，不重复索要“设计通过”“计划通过”。只要求评估、方案或分流时不算实现授权；确需新授权时，先准备好可审阅的范围与方案再询问。
- **实现、提交、推送分别记录授权范围。** 明确的“修复后提交并推送”可以一次授权，范围未变时不重复询问；只有修复请求时不推定提交或推送已获授权。原卡的批准不自动授权本次修改，推送仍受本次验证与评审结果约束。
- 恢复已有维护卡时，先核对 README 与维护记录中的范围、授权、工作区差异、已完成验证和阻塞；仅继续本次未完成事项，不把新问题并入旧授权。`done` 记录只供追溯，新问题另建关联记录。
- 本路径可以在同一窗口连续完成；不需要另建 01–06、T01、设计图或两份评审报告。项目确需的 QA / 发布检查在维护记录中留证据；需要新设计或新业务决议时升级。

## 执行与验证

1. **核实并记边界。** 按 [规范索引](../spec/index.md) 读取相关章节，引用原卡的有效 AC / 契约与当前实现证据。行为缺陷先按 [调用链核查](implementation-principles.md#修复前核查调用链) 查明相关调用方、根因证据与拟修位置，区分受影响和不受影响的入口及其依据；必要路径未知时不能认定影响已界定。写清复现、期望、计划改动范围、回归方式、恢复方式和文档影响。记录当前工作区差异，保留已有改动，不将无关文件混入本次交付。同步代码遵守项目约定，脏工作区先确认安全同步方式。
2. **复现后最小修复。** 行为缺陷先得到能体现问题的失败测试或可复现步骤，再按 [最小实现阶梯](implementation-principles.md#最小实现阶梯) 修复，验证报错入口、其他受影响入口及需保持的行为。已有回归足够时复用，缺少覆盖才补测试；无自动化条件时记录可重复的人工步骤和证据。只有存在实际取舍时按 [简化边界规则](implementation-principles.md#有意简化的边界) 记录当前足够的依据、已知上限与重新评估条件；仍须满足轻量条件，不能以留下后续事项规避本次验收。原因或影响扩大则重新分流；不强制凑多个假设或拆子任务。
3. **验证并回写。** 运行相关回归与项目必需门禁。失败、未运行和环境限制如实记录，不能用预计结果代替。现行说明确有变化时及时更新；没有文档影响则写明原因，按 [项目文档维护](documentation.md) 核对证据和适用范围。
4. **针对实际差异评审。** 查看本次完整 diff，记录基准修订与改动文件，核对预期覆盖、范围、回归证据、工程约束、文档一致性和升级条件。行为缺陷检查调用方核查是否支持修复位置与覆盖范围；有意简化时检查上限、重新评估条件及已实施限制的文档回写。可由当前窗口复查并如实写评审者，不强制换窗口或双代理；项目要求独立评审时照做。有必改项时不通过；后续修改重新检查受影响部分，并更新评审范围。
5. **按授权交付。** 验证与评审通过后执行已授权的提交 / 推送，按项目分支和发布约定操作；需要新授权时展示具体差异、验证结果和交付动作。推送前重新确认待推送提交均在授权与已审范围内，不带无关提交。记录提交号、推送目标及部署 / 环境验证事实，推送成功不等于已部署或已验收。
6. **收尾。** 本次目标、必需验证、评审、文档回写及承诺的交付已完成后，设 `done`，按 [归档规则](../cards/README.md#归档) 归档，追加一条简短 journal 并记录沉淀去向。只要求本地修复时，明确未提交 / 未推送 / 未验证部署；若本次承诺包含环境验证或项目要求 QA，须取得结果后才能完成。以后新增问题另建关联记录。

## 升级到完整流程

1. 停止本次实现和推送，保留现有代码差异、失败 / 通过证据及用户已有改动，不自动撤销或删除。维护记录写明触发原因、新发现的影响、尚未完成的验证与原授权不再覆盖的部分。
2. 在**同一卡目录**将 `workflow` 改为 `full`，保留 ID、原卡链接和 `maintenance.md` 作为历史依据；本地维护标识可保留，取得外部编号后补链接。整理 `01-card.md`，复用已核实的事实和原 AC；按 [卡分析模板](../templates/card-analysis.md) 的澄清记录部分建立 `02-questions.md`，记录已有决定及来源、未知项和已完成的复核。没有待问事项时写明依据，不虚构问答或 Dev 审阅，不重复提问已确定的内容。
3. 根据缺口设置完整流程的入口：需求 / 范围仍有问题用 `clarifying`；预期明确但本次尚无有效 03 批准用 `aligning` 并整理 03 草稿；只有本次范围已有可核实的有效 03 批准、仅需设计调整时才用 `planning`。列明下一步的 `clarify` / `align` / `dev-plan` 命令，不自动调用后续阶段。
4. 补齐完整流程实际需要的批准与产物，不能把维护实现授权或历史卡的批准伪装成新 03/04 批准。现有代码按修订后的计划重新核对并纳入评审，不能因已经写好就跳过门禁。后续跟踪以完整阶段文档为准，维护记录冻结为升级时的快照并留新入口指针；不再切回轻量规避门禁。

## 虚构示例

- 列表筛选遗漏了已约定的一个状态，问题在单仓库局部逻辑，回归可覆盖且不改契约：可评估轻量。
- 帮助文档中的链接或展示文字拼写错误，业务含义不变：可评估轻量，验证链接 / 展示即可。
- 修一个条件判断却改变了访问权限：升级完整流程，即使只改一行。
- 原以为只改显示，查证后需要调整共享枚举或历史数据：记录现状并升级，不能继续沿用轻量授权。

真实业务证据留在目标项目受控位置；对外基线只使用通用规则或虚构示例。
