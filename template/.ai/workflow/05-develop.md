# 05 · 开发：协调与评审（Develop）

按已批准的 `04-dev-plan.md`，把子任务派给执行者，逐批评审，合并到本地主分支并提交，做集成评审，最后组织卡级代码评审（`05-card-review.md`），通过后才推送。本窗口用顶级模型；写代码的是执行者，按 `05-execute-subtask.md` 工作，可以是低端模型的子代理，也可以是用户新开的窗口。

## 进入条件

- 卡目录 `README.md` 的 `stage` 是 `ready-for-dev` 或 `in-dev`，且 `04-dev-plan.md` 的"批准记录"有拆解确认（批准人、日期、原话）。没有就不开工，提示用户回到 04。
- 已按 `session-protocol.md` 开场（`git pull` 到最新）。
- 第一次进入时把 `stage` 改为 `in-dev`，按 `templates/dev-log.md` 建 `05-dev-log.md`。
- 读 `04-dev-plan.md` 的“文档影响与回写”和 [项目文档维护](documentation.md)，确认维护分工。旧卡缺该清单时按已批准范围补录文档影响，不补造历史状态或批准。

## 分支与提交

- 直接在主分支开发（以远端默认分支为准），不建远端功能分支。发布分支与 CI 规则见 `spec/config-and-deploy.md`。
- 每次修改文件前先 `git pull`；pull 出冲突先停下解决。
- 同一仓库并行时允许本地临时 worktree（见下）；临时分支只在本地，不推送，合并回本地主分支后删除。
- 提交信息：以 `git log` 核实过的团队惯例为准（落地时把真实格式写在这里，含卡号格式与例）。拿不准先 `git log --oneline -15`。
- 提交由用户确认：一次性给出分批提交计划（一个子任务或一个逻辑改动一个提交，列出文件），用户回"ok"才执行；用户开场给出"本卡提交照此执行"的一次性授权时，逐批不再重复确认。不 amend。**推送**：本卡提交在卡级代码评审通过之前只留在本地主分支；评审通过后给出推送建议，用户确认才 push（推送前再核对一次迁移版本号）。用户坚持提前推送时，把原因记进 `05-dev-log.md`。不认识的脏文件单独列出请用户确认，不要静默带上。

## 每一轮做什么

1. **看前沿。** 读 `tasks/` 下各子任务单的状态，找出依赖都已"通过"的"待执行"或"返工"子任务，按批次分组。
2. **定串行还是并行。**
   - **默认串行**：在主工作区一次执行一个子任务，评审通过、提交之后再做下一个。
   - **前后端并行**：两个仓库的子任务天然隔离，可以直接同时执行。
   - **跨仓库并行优先；同一仓库并行是例外**：只有同一批次、改动文件互不重叠、且各自有独立验证命令时才可以，而且每个子任务一个本地 worktree。先把卡目录的计划文档提交到本地主分支（提交计划照常由用户确认），再从最新的本地主分支创建：
     ```bash
     git worktree add ../<仓库名>-wt-<卡号>-<T编号> -b wt/<卡号>-<T编号>
     ```
     把 worktree 路径写进子任务单的"工作目录"，这一步在创建 worktree 之前、于主工作区完成并随计划文档提交，worktree 里的副本才带着正确的工作目录。前端类仓库的 worktree 先装依赖（如 `npm ci`）。
     **worktree 存续期间，这张子任务单以 worktree 里的副本为准**：执行者写那份，协调窗口也到那份里看状态、写评审记录；主工作区里的同一张单子不动，否则 squash 合并时会冲突。
   - **不要在同一个工作区里并行**：单模块工程的编译与测试是全局的（后端编译、前端类型检查都覆盖整个项目），一个子任务写到一半，其他子任务的编译和测试都会失败。
3. **派发。** 派发内容只给指针，与用户在新窗口里输入的话等价：
   ```
   你是本卡的执行者。按 <仓库>/.ai/workflow/05-execute-subtask.md 执行子任务单 <卡目录>/tasks/T03-<slug>.md。
   ```
   - 工具支持子代理时，派子代理执行；工具能给子代理指定模型时，按子任务单的"执行者建议"选。
   - 工具不支持，或者用户想自己开窗口时，告诉用户要开哪几个执行窗口：工作目录、命令 `execute-subtask <卡目录> <T编号>`、建议模型。
   - 标"需顶级模型"的子任务，派给顶级模型的子代理，或由本窗口按执行者协议亲自执行，同样写执行记录、同样过评审。
   - 不在派发语句里附加聊天中的额外说明。需要补充的信息，先写进子任务单再派发。
4. **评审。** 子任务状态变为"待评审"后逐个评审，见下文。在 worktree 里执行的子任务，到 worktree 里读单子、跑验证、写评审记录。
5. **合并与提交。** 评审通过的子任务给出提交计划，用户确认后提交到主分支。worktree 里的子任务，在用户确认后先在临时分支提交，（子任务单的执行与评审记录一起提交），回到主工作区执行 `git merge --squash wt/<卡号>-<T编号>`，再用确认过的提交信息提交；然后 `git worktree remove` 并删除临时分支。每批合并完，在主工作区跑一次全量门禁。
6. **回写项目文档并更新开发记录。** 每批集成验证后，协调者按计划清单更新已变化的现行事实、受影响的引用和契约镜像，记录核实依据与验证范围；尚未实施的部分留在计划。实际发现的新文档影响补入清单，最迟在卡级评审前完成本卡已实现变化的回写。状态与证据回填 04；`05-dev-log.md` 记录清单指针、子任务状态、提交号、偏差和下一批。文档改动纳入提交计划。
7. **收尾。** 按 `session-protocol.md` 打印下一步：还有未完成的子任务，就写下一批怎么派发或要开哪些执行窗口；全部通过，就进入集成评审。

## 评审（每个待评审的子任务）

1. **重跑验证。** 自己跑子任务单的验证命令，不以执行者的自述为准。
2. **核对范围。** 在工作目录里看 `git status --short` 与 `git diff --name-only`，改动文件必须都在"可改文件"清单内。
3. **对照契约。** 签名、字段名、表结构、配置键、日志前缀与 `04-dev-plan.md` 的契约一节一致。
4. **对照用例与 AC。** 测试落在约定的测试缝上；期望值独立于实现，不是把实现逻辑再算一遍；用例表里的用例一个不少。
5. **对照规范。** 命名、分层、时区（按本仓库时间约定）、日志与脱敏、异常处理符合 `spec/`。
6. **写结论。** 结论写进子任务单的"评审记录"：
   - **通过**：状态改为"通过"。
   - **返工**：逐条写清问题（文件:行号与期望），状态改为"返工"，再派一次，同样只给指针。
   - **小问题**：评审者可以直接改，记进评审记录。
   - **计划本身有问题**：按 `04-dev-plan.md` 的"批准后的变更"处理。
7. **处理阻塞。** 子任务状态为"阻塞"时，读执行记录里的问题：能通过修改子任务单解决的（补契约引用、补用例、补可改文件），改完把状态改回"待执行"再派；要改设计的，退回 04。

## 集成评审（全部子任务通过后）

- **全量门禁**：主工作区跑本仓库的门禁命令，跨仓库卡两边都跑。
- **跨子任务一致性**：调用链是否接通，有没有重复实现，子任务之间的约定有没有漂移。
- **AC 覆盖**：按 `04-dev-plan.md` 的 AC 追踪表逐条核对，每条 AC 都有测试或手工证据，写进 `05-dev-log.md` 的"自测证据"。
- **范围纪律**：有没有追溯不到 AC 的改动，有没有为不存在的场景加抽象或配置，有没有把修复放在调用方而不是行为真正所在处。
- **文档一致性**：对照 04 的文档清单，检查实际 diff 是否还影响其他主题；现行说明与实现、批准的偏差一致，历史已标替代关系，核实范围和共享契约来源准确。已实现行为的文档项须为“已更新”或有依据的“无需更新”，不能以等待结卡代替。
- **清理**：临时 worktree 与本地临时分支已删除，临时日志已清掉。
- 结果写进 `05-dev-log.md`。

## 卡级代码评审与推送

集成评审通过后，按 `05-card-review.md` 组织两轴评审（Spec 轴、Standards 轴，全新上下文的子代理或用户新开的两个窗口），产出 `05-card-review.md`。必改项处理完、结论为"通过"后，给出推送建议，用户确认后 push。然后把 `stage` 改为 `desk-check`，按 `session-protocol.md` 收尾（下一个窗口：`desk-check`）。

## 完成标准

- 所有子任务状态为"通过"，提交已由用户确认并执行（或用户选择自己提交）。
- 集成评审通过，门禁绿，每条 AC 有证据。
- 本卡文档影响已核对并回填证据，相关文档变更已纳入卡级评审；未部署和待环境验证的范围已如实标明。
- 卡级代码评审结论为"通过"，推送已由用户确认。
- `stage: desk-check`。

## 常见错误

- 执行者自述"测试已通过"就放行，没有重跑验证命令。
- 在同一个工作区里并行派发多个子任务，彼此的半成品让编译失败。
- 派发时在聊天里补充了单子上没有的要求，换个窗口执行就不一致了。
- 子任务阻塞时评审者直接改设计，而不是退回 04 重新确认。
- 子任务评审一通过就推送，卡级代码评审还没做，问题要到 dev 部署后才发现。
