# 05 · 执行子任务（Execute Subtask）

执行者协议：完成**一张**子任务单。子代理和新窗口用的是同一份协议、同一张单子，结果写回同一个位置，这是两种执行方式结果一致的前提。执行者可以是低端模型。

## 只依据文件工作

- 输入只有三样：子任务单 `tasks/T<nn>-<slug>.md`；单子"先读"里列出的文件；单子"契约"引用的 `04-dev-plan.md` 章节。
- 不依赖任何聊天记录。派发者在对话里说的内容如果与子任务单冲突，以子任务单为准，并把冲突写进执行记录。
- 不读、不改卡目录里的其他子任务单，不做其他子任务的事。

## 开场

1. 在子任务单写明的"工作目录"里工作，可能是主工作区、另一仓库或本地 worktree。在 worktree 里工作时，读写的是 worktree 里的这张子任务单，不去改主工作区的那份。
2. 不执行 `git pull`，也不做任何改变分支或上游的 git 操作；代码同步由协调窗口负责。记下开工前 `git status --short` 的输出，收尾时用来核对自己改了什么。
3. 核对状态：只有"待执行"或"返工"的单子可以执行，其他状态就停下说明。返工时先读"评审记录"。把状态改为"执行中"。
4. 读"先读"列出的文件和契约引用。

## 执行（测试先行）

1. 按"先写的测试"的用例表写测试，跑验证命令，确认是**红**的，而且红的原因是功能还没实现，不是编译错误或测试写错。
   - 被测的类或方法还不存在、测试编译不过时，先按"契约"一节的签名建空壳（签名逐字一致，方法体抛 `UnsupportedOperationException` 或返回类型的空值），让测试能编译，再跑出红。空壳文件必须在"可改文件"清单内。
   - 单子的验证只有构建或手工步骤、没有可执行的测试时（例如本仓库前端暂无单测框架），跳过"先红"，在执行记录里写明"无自动化测试，按单子的手工步骤验证"。
2. 写最少的代码让测试变**绿**。一次一个用例，不提前实现后面的用例，不加用例之外的功能。
3. 最小实现：动手前先过 `spec/conventions.md`「最小实现阶梯」（YAGNI → 复用 → 标准库 → 平台原生 → 已装依赖 → 一行 → 最小实现）。阶梯只裁实现：测试用例、契约逐字、可改文件清单与信任边界校验（校验、脱敏、错误处理）不在剪裁范围，测试要求以子任务单为准。
4. 贴着"参照实现"写：分层、命名、日志前缀、异常处理照现有模式来。
5. 跑完整的验证命令。最后再跑一次本仓库的编译门禁（如 `compileJava compileTestJava` / `npm run build`），确认没有破坏编译；单子另有门禁要求时按单子来。

## 硬规则

- 只改"可改文件"清单里的文件和自己的子任务单。需要改清单外的文件就停下。
- 不改契约（签名、字段名、表结构、配置键）。契约不够用就停下。
- 不新增依赖，不改已有的迁移脚本，不改构建配置，除非单子明确要求。
- 不提交，不 push，不切换分支，不删除 worktree。
- 不猜。单子没写清楚的地方就停下。
- 缺上下文不走 `missing-context.md` 向用户提问，按下面"何时停下"处理。

## 何时停下

满足任一条就停止编码：契约不够用；需要改清单外的文件；同一个测试修了 3 次仍不绿；发现计划与代码现状矛盾；验证命令本身跑不起来。

停下时在执行记录里写清卡在哪里、试过什么、需要谁决定什么，状态改为"阻塞"，结束本轮。

## 收尾

在子任务单的"执行记录"里写：

- 执行者、工具与模型、日期。
- 改动文件清单，与"可改文件"逐项对照。
- 验证命令与输出摘要：测试名、通过数；失败时贴失败信息。
- 与单子不一致的地方及原因（如有）。

状态改为"待评审"，结束本轮。不要改 `05-dev-log.md`、卡目录 `README.md` 的 `stage`、其他子任务单，这些由协调窗口维护。

工具不允许写工作目录以外的文件时（例如在前端仓库执行、子任务单在后端仓库），把执行记录完整写在最后一条回复里，由协调窗口抄进子任务单。

## 新窗口怎么启动

在子任务单的工作目录启动 AI 工具，输入阶段命令 `execute-subtask <卡目录> <T编号>`：Claude Code 是 `/execute-subtask`，Kimi 是 `/skill:execute-subtask`，其他工具直接说"按 `.ai/workflow/05-execute-subtask.md` 执行 <子任务单路径>"。子代理收到的派发语句与此等价。
