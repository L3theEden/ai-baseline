# 卡片开发流程总览

一张卡从 BA 开出到 QA 关闭，经过七个阶段。卡是 BA 拆好的交付单元，开发的目标就是完成这张卡的验收标准（AC），不多做也不少做。每个阶段有固定的输入、产物和门禁；产物全部落在 `.ai/cards/<卡目录>/` 里，聊天记录只是过程。

## 一个窗口只做一个阶段

每个阶段在一个新的会话窗口里运行，窗口可以换 AI 工具、换模型。开场与收尾按 `session-protocol.md`：

- 开场先读卡目录 `README.md` 的 `stage`，只做与之匹配的阶段。
- 收尾写产物、改 `stage`、记 journal，打印"下一步"（下一个窗口在哪里启动、输入什么命令、建议什么模型），然后结束。
- **AI 永远不自行进入下一阶段。** 用户说"继续""没问题就开发"也不行；下一阶段只能由用户用阶段命令触发。
- 阶段命令是 `.claude/skills/`、`.agents/skills/` 里的薄壳，只能由用户调用，模型不会自己触发。

## 阶段一览

| # | 阶段 | 阶段命令 | 建议模型 | 输入 | 产物 | 门禁（过了才进下一阶段） | 手册 |
|---|---|---|---|---|---|---|---|
| 01 | 读卡 | `card-intake` | 任意 | 用户粘贴的卡内容 + 卡号 | `README.md`、`01-card.md` | 卡里的说法已核实；缺上下文已按协议处理 | `01-card-intake.md` |
| 02 | 拆问题 | `clarify` | 任意 | `01-card.md` + spec / legacy / 上下游 + 已有问答 | `02-questions.md`（交互记录、本轮 BA 问卷、价值质疑） | 默认先与 Dev 交互并逐轮复核，本轮问卷经 Dev 审阅后带去与 BA 对齐 | `02-clarify.md` |
| 03 | 对齐 | `align` | 任意 | BA 的答复 | `03-alignment.md`（验收标准、范围、决议） | 用户在独立一条消息里批准，`stage: planning` | `03-align.md` |
| 04 | 制定开发计划 | `dev-plan` | 顶级 | 已批准的 `03-alignment.md` | `04-dev-plan.md`、`tasks/T<nn>-<slug>.md` | 设计确认、拆解确认两道批准，`stage: ready-for-dev` | `04-dev-plan.md` |
| 05 | 开发 | `develop`（协调与评审）、`execute-subtask`（执行）、`card-review`（卡级代码评审） | 协调评审用顶级；执行可用低端 | 已批准的开发计划与子任务单 | 代码、测试、子任务单的执行与评审记录、`05-dev-log.md`、`05-card-review.md` | 全部子任务评审通过、集成评审通过、门禁绿、卡级代码评审通过后才推送，`stage: desk-check` | `05-develop.md`、`05-execute-subtask.md`、`05-card-review.md` |
| 06 | DC | `desk-check` | 任意 | `03`、`04`、`05` 的产物与测试输出 | `06-desk-check.md` | DC 会议通过，`stage: in-qa` | `06-desk-check.md` |
| 07 | 交 QA / 结卡 | `qa-handoff` | 任意 | QA 结果 | `06-desk-check.md` 回填、journal、spec 回写 | 全部 AC 通过，`stage: done`，卡目录归档 | `07-qa-handoff.md` |

02 与 03 可以在同一个窗口完成：问卷发出、BA 答复回来后，用户在同一窗口输入 `align`；BA 隔天才答复就新开窗口。

02 默认先与 Dev 澄清其能回答且有权决定的部分，再整理待 BA 决定的本轮问卷；明确要求直接出问卷时可跳过访谈。每批答复后都复核新问题、依赖、冲突和验收缺口，必要时在 02 与 03 之间多轮往返。产出问卷不表示需求已经收敛；03 无待展开关键题且通过收敛门禁后，才呈现摘要请求批准。

横切协议：开场、收尾、阶段中途换窗口走 `session-protocol.md`；缺上下文走 `missing-context.md`。

## 卡状态机

```
intake → clarifying → aligning → planning → ready-for-dev → in-dev → desk-check → in-qa → done
```

- `clarifying`：正在交互澄清、审阅问卷草稿，或需要展开下一轮问题。
- `aligning`：本轮问卷已审阅并等待答复，或已收到答复正在整理对齐文档；仍可存在未答问题。
- `planning`：对齐已收敛并批准，等待或正在制定开发计划。
- `ready-for-dev`：开发计划已通过拆解确认，可以开始 05。

回流：

- 答复引出新问题或解锁待展开题：`aligning` 回到 `clarifying`；保留既有编号和答复，整理下一轮。仅等旧题答复时保持 `aligning`。
- 已批准对齐后发现影响原结论的关键新问题：按需回到 `clarifying` 或 `aligning`，标明原批准不覆盖的变更，重新收敛并批准后再向下游推进。
- 开发中发现设计要改（新表或字段、新接口、新依赖、新配置、范围变大）：`in-dev` 回到 `planning`，改计划并重新确认。
- DC 未通过或 QA 发现本卡 AC 范围内的缺陷：回到 `in-dev`；是设计问题回到 `planning`；AC 本身有问题回到 `aligning`。
- 超出本卡 AC 的缺陷：新开 fix 卡，`links` 引用原卡，原卡不因它阻塞。

- **分期卡**（A/B/C 或一期/二期，01 已固定分期词表）：`stage` 表示**当前期**的位置。新一期开始时，上一期的 03/04/05 等产物加期号后缀留档（如 `03-alignment-A-20261014.md`）或移入 `research/history/`，当前文件写本期内容，README 写明当前期；本期对齐批准后进入 `planning`。门禁按期独立：上一期未 DC、未 QA 不阻塞下一期制定计划；已答问题按词表引用，不重问。

状态写在卡目录 `README.md` 的 frontmatter `stage:` 字段，它是唯一状态源。任何阶段发现前一阶段的产物有错，回去改产物（需要时重新批准），再前进。

## 角色

- **BA**：开卡与拆卡、回答问卷、批准对齐文档、参加 DC。
- **Dev**（与 AI 一起）：读卡、拆问题、对齐、确认开发计划、确认提交、写 DC、交 QA、结卡回写。技术取舍由 Dev 拍板。
- **QA**：依据 `03-alignment.md` 的验收标准和 `06-desk-check.md` 的演示脚本测试；缺陷回流。
- **AI**，按窗口分三种角色：
  - 规划者（01 到 04，以及 05 的协调，用顶级模型）：事实自己查，决策交给人。
  - 执行者（05 执行，可用低端模型，子代理或新窗口都可以）：只依据子任务单工作。
  - 评审者（05 协调窗口内，用顶级模型）：重跑验证，按契约、AC、spec 审查执行结果。

## 四条不可让步的规则

1. **批准只放行下一个阶段。** 建卡目录、对齐批准都不是开发许可；只有 `04-dev-plan.md` 的拆解确认记录在案，才能写业务代码和迁移脚本。
2. **一个窗口只做一个阶段，AI 不自行推进。** 阶段之间只靠卡目录里的文件交接。
3. **能查到的不要问。** 代码、配置、测试、git 历史、`.ai/` 文档能回答的，AI 自己查并写明证据；只把产品意图、范围边界、技术与风险取舍留给人。
4. **每个阶段的结论都写进文件。** 执行者看不到聊天记录；没写进卡目录的结论等于没发生。

## 一张卡的文件集

```
.ai/cards/feat-DEMO-123-task-status-filter/
├── README.md          # frontmatter：id / type / title / stage / primary_repo / linked_repo / created / links
├── 01-card.md         # 规范化后的卡 + 核实结果 + 影响面初判
├── 02-questions.md    # 给 BA 的问卷 + 价值质疑
├── 03-alignment.md    # 最终验收标准、范围内外、决议、批准记录
├── 04-dev-plan.md     # 技术设计、契约、AC 追踪、测试设计、子任务图、单向门、两道批准记录
├── tasks/             # 子任务单，一个子任务一个文件：T01-<slug>.md …
├── 05-dev-log.md      # 子任务状态汇总、批次与 worktree、偏差、提交、集成评审、自测证据
├── 05-card-review.md  # 卡级代码评审：评审范围、Spec 轴与 Standards 轴报告、分流、推送确认
├── 06-desk-check.md   # 逐条验收标准的演示与证据、部署前置、QA 关注点、QA 结果回填
├── context-notes.md   # 可选：缺上下文的补全记录
├── research/          # 可选：一题一文件的调研（外部 API 实测、对端代码）
└── assets/            # 可选：截图、样例请求
```

跨仓库的卡：文档放主改动仓库（改动多的一方）；另一仓库同名目录只有一个 `README.md`，写明主仓库路径与本仓库改动摘要。另一仓库的子任务单仍放在主仓库卡目录，工作目录写另一仓库。
