# 03 · 对齐（Align）

逐轮回填答复并维护 `03-alignment.md`（模板：`.ai/templates/alignment.md`），问题收敛并获批准后成为定稿。这份文档是后续开发、DC、QA 测试共同的依据，相当于本卡的 PRD。部分答复可以先记录，未收敛时明确标为草稿。

## 输入

- BA 或有权 Dev 对 `02-questions.md` 的答复（用户粘贴，或在交互式 grill 中逐题回答），以及已有问卷、轮次记录和对齐草稿。
- 若答复引出新问题：先保留本轮明确结论，再回到 02 整理下一轮。草稿可以记录开放问题，不能把它们带入已批准的定稿。

## 步骤

收到用户显式的 `align` 指令并确认已有问卷后，进入本阶段记为 `aligning`；若复核发现需展开下一轮，再按下文回到 `clarifying`。草稿尚未经过 Dev 审阅但用户已提供对应答复时，也先如实回填，不要求重复访谈。

1. **回填并复核答复。** 逐题把原话、答复人、日期及来源写进 `02-questions.md`，没有提供的来源信息如实标明，不补造。当前理解与原话分开；范围、口径、做法类答复先回述理解，交互式当场确认，异步答复在摘要里单列"我的理解"供核对，未确认或有歧义的保留为待澄清。
   - **阻塞**题必须有逐题的明确答复。BA 只回了"按建议来"之类的笼统答复时，阻塞题视为未答，继续追问。
   - **可默认**题只有在有权答复者明确接受建议后才按推荐通过，在决议表标"按推荐"并保留接受的建议版本；未答不视为同意。
   - Dev 的意见不自动等于 BA 决议；无权决定的答复、含糊答复和互相冲突的答复保留待澄清。原决定被明确修订时，保留旧答复与修订来源。
   - 每批答复后按 02 的"每轮答复后的复核"检查新问题、依赖、冲突和验收缺口，不能只核对已有题是否填满。范围确认后仍在范围内的待展开题进入下一轮，移出范围的题标"本期不适用"并写入范围外。
   - 仅缺旧题答复时保持 `aligning`；需要展开新一轮问题时改为 `clarifying`，保存问卷、对齐草稿和轮次记录，提示用户输入 `clarify`，不自行触发阶段命令。新题编号递增，旧题不重排、不覆盖。
   - 术语的结论写进对齐文档的"术语"一节。
2. **改写为对齐文档。** 按模板产出：
   - 需求理解：一段话说明要做什么、为谁、为什么。
   - 验收标准（AC）：Given / When / Then，每条独立可验证，编号 `AC-1`… 并跨轮保留；QA 将逐条测试。注明对应 Q 或原卡依据，受未答题影响的只能标为草稿。
   - 范围内 / 范围外：范围外要具体到"不做 X"，防止后续扩散。
   - 决议与理由：每个问题的最终决定和 BA 给的理由。
   - 被否决的质疑：AI 提出但 BA 不接受的点，记录理由；符合条件的同步写入 `.ai/decisions/rejected/`。
   - 风险与依赖：上下游、配置预建、数据迁移、发布顺序。
   - 开放问题：允许为空；不为空则不能通过门禁。
3. **收敛门禁。** 逐项检查（借自 Trellis 的 requirement convergence gate）：
   - 用户价值和业务目标已明确。
   - 范围内外已明确。
   - 每条 AC 描述的是可观察的结果，而不是实现方式。
   - 所有产品、范围、交互、兼容、风险决策都有决议。
   - 所有阻塞题有有权者的明确结论，没有待展开的关键问题、未处理的关键质疑或答复冲突；本轮复核没有留下影响范围与 AC 的新缺口。
   - 开放问题为空。
   - 技术未知项要么已调研（写在 `research/`），要么明确推迟且不改变 AC。
4. **收敛后重写一遍。** 把临时段落（"我已知道的""假设""已解决的问题"）折进正式段落；不重复同一事实；不丢任何决议、AC 编号、证据路径。
5. **收敛后呈现最终摘要并停下。** 门禁未过时，只汇报已确认部分、开放问题、待展开 Q 及下一步，不请求定稿批准。门禁全过后，向用户展示：目标、范围内、范围外、AC 列表、关键决议、明确按推荐通过的题、风险；然后**结束本轮**。不要在同一条回复里开始制定开发计划或写代码。
6. **等待明确批准。** 只有用户在**后续一条新消息**里明确批准这份摘要（例如"对齐通过"），才把 `stage` 改为 `planning`，并在文档"批准记录"写上批准人、日期与原话。用户最初"帮我做这张卡"的请求、建卡目录时的同意、"没问题的话就……"这类条件句，都不算批准。对齐批准只放行 04 制定开发计划，不是开发许可。
7. **收尾。** 按 `session-protocol.md` 打印下一步（下一个窗口：`dev-plan`，建议顶级模型），结束本轮。不要在本窗口开始制定开发计划，也不要建分支、写代码。
8. 批准后若对齐文档有实质修改，或出现影响原结论的关键新问题，按需回到 `clarifying` 或 `aligning`，注明原批准不覆盖哪些变更；重新复核收敛门禁并走 5–6。重新批准时，原批准记录标"已被 <日期> 修订取代"，新记录带修订版本（如 03 v2），下游引用批准写明版本。

## 完成标准

- `03-alignment.md` 无"待定"，AC 有编号且可测。
- "批准记录"段有批准人、日期与原话。
- `stage: planning`。

## 常见错误

- 把 BA 的一句"可以""按建议来"当成对所有问题的答复。阻塞题逐题要答复，没答的继续追问。
- 当前列表答满就请求批准，没有复核待展开题、新增场景和受影响的 AC。
- AC 写成"实现 XX 功能"。AC 必须是用户或系统可观察的行为。
- 批准前顺手改了代码。对齐阶段不碰业务代码。
- 把对齐批准当成开发许可，在同一窗口接着写开发计划、建分支或写代码。对齐批准只放行 04，04 在新窗口进行。
