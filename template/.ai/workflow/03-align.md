# 03 · 对齐（Align）

逐轮回填答复并维护 `03-alignment.md`（模板：`.ai/templates/alignment.md`），问题收敛并获批准后成为定稿。这份文档是后续开发、DC、QA 测试共同的依据，相当于本卡的 PRD。部分答复可以先记录，未收敛时明确标为草稿。

## 输入

- BA 或有权 Dev 对 `02-questions.md` 的答复（用户粘贴，或在交互式 grill 中逐题回答），以及已有问卷、轮次记录和对齐草稿。
- 没有新增答复，但原卡和已有明确来源已覆盖全部关键决定时，可据此检查收敛；记录所用依据，不为凑问答虚构 BA 答复。最终摘要和后续明确批准仍须完成。
- 若答复引出新问题：先保留本轮明确结论，再按 02 的设计树规则直接追问下一轮。草稿可以记录开放问题，不能把它们带入已批准的定稿。

## 默认连续澄清与对齐

用户启动 `align` 后，本卡的答复回填、逐轮复核、设计树追问与结论更新属于同一个需求问答循环。发现新问题时直接读取并复用 `02-clarify.md`，不要求用户重新输入 `clarify`，也不自行调用阶段 skill。用户在同一聊天直接回答即可继续；换窗口时用 `align <卡目录>` 读取文件续接，包括 `stage: clarifying` 的对齐中澄清轮次。

每轮把前置条件已满足、当前用户能够且有权回答的问题一起列出，附依据与建议，等待答复后再重算依赖。用户不知道或无权决定的题整理成本轮 BA 问卷，先交用户审阅、由用户转发，再等待有权者答复；不反复要求用户代答。用户明确要求只回填、暂停追问或直接整理问卷时按其要求处理，开放问题照实保留，不因此宣称收敛。

本循环止于关键问题收敛后的对齐批准；进入 `dev-plan` 仍需用户另行触发。

## 步骤

收到用户显式的 `align` 指令并确认已有问卷后，进入本阶段记为 `aligning`；若复核发现需展开下一轮，改为 `clarifying` 并在本循环内继续。`stage` 记录实际进度，状态变化不要求用户切换命令。草稿尚未经过 Dev 审阅但用户已提供对应答复时，也先如实回填，不要求重复访谈。

1. **回填并复核答复。** 逐题把原话、答复人、日期及来源写进 `02-questions.md`，没有提供的来源信息如实标明，不补造。当前理解与原话分开；范围、口径、做法类答复先回述理解，交互式当场确认，异步答复在摘要里单列"我的理解"供核对，未确认或有歧义的保留为待澄清。
   - **对应关系与版本。** 先核对答复对应哪个 Q、哪一轮 / 哪版题干与建议；没有编号但对应关系唯一明确时可映射并说明依据。存在多种对应、或旧版答复无法覆盖新版改动时，保留为待映射 / 待澄清，只追问受影响部分，不覆盖已有记录，也不阻塞其他明确答复的回填。
   - **阻塞**题必须有逐题的明确答复。BA 只回了"按建议来"之类的笼统答复时，阻塞题视为未答，继续追问。
   - **可默认**题只有在有权答复者明确接受建议后才按推荐通过，在决议表标"按推荐"并保留接受的建议版本；未答不视为同意。
   - Dev 的意见不自动等于 BA 决议；无权决定的答复、含糊答复和互相冲突的答复保留待澄清。原决定被明确修订时，保留旧答复与修订来源。
   - 每批答复后执行下文的"本轮复核结果"，检查新问题、依赖、冲突和验收缺口，不能只核对已有题是否填满。新答复改变技术前提或与旧证据冲突时，重新查证受影响的事实；技术现状与产品期望分开记录。前置明确后，仍在范围内的待展开题、待细化领域进入下一轮，移出范围的题标"本期不适用"并写入范围外。
   - 仅缺旧题答复时保持 `aligning`；需要展开新一轮问题时改为 `clarifying`，先保存问卷、对齐草稿和轮次记录，再直接按设计树提出当前可回答的下一轮问题。收到答复后继续回填、复核并更新结论；澄清结束、问卷审阅完成后回到 `aligning`，无需再次输入 `align`。新题编号递增，旧题不重排、不覆盖。
   - 术语的结论写进对齐文档的"术语"一节。
2. **改写为对齐文档。** 按模板产出：
   - 需求理解：一段话说明要做什么、为谁、为什么。
   - 验收标准（AC）：Given / When / Then，每条独立可验证，编号 `AC-1`… 并跨轮保留；QA 将逐条测试。注明对应 Q 或原卡依据，受未答题影响的只能标为草稿。
   - 范围内 / 范围外：范围外要具体到"不做 X"，防止后续扩散。
   - 决议与理由：每个问题的最终决定和 BA 给的理由。
   - 被否决的质疑：AI 提出但 BA 不接受的点，记录理由；符合条件的同步写入 `.ai/decisions/rejected/`。
   - 风险与依赖：上下游、配置预建、数据迁移、发布顺序，以及有依据的推迟项、影响与后续处理。未答业务题的推迟必须有有权者的明确决定；不能由 AI 自行移出开放问题。
   - 开放问题：允许为空；不为空则不能通过门禁。
3. **收敛门禁。** 逐项检查（借自 Trellis 的 requirement convergence gate）：
   - 用户价值和业务目标已明确。
   - 范围内外已明确。
   - 每条 AC 描述的是可观察的结果，而不是实现方式。
   - 所有产品、范围、交互、兼容、风险决策都有决议。
   - 所有阻塞题有有权者的明确结论，没有待展开关键题、影响范围或 AC 的待细化领域、未处理的关键质疑或答复冲突；本轮复核没有留下关键新缺口。
   - 开放问题为空。
   - 技术未知项要么已调研（写在 `research/`），要么由 Dev 明确评估可推迟，记录依据、影响与后续处理，且不改变本期范围或 AC；依赖它的关键判断不能靠假设通过。
4. **收敛后重写一遍。** 把临时段落（"我已知道的""假设""已解决的问题"）折进正式段落，每题保留一个当前有效决议，移除已解决的开放项，不重复同一事实；历史答复与修订依据留在问卷，结论按需引用，旧批准记录保留。不丢决议依据、Q / AC 编号、证据路径与推迟项。
5. **按复核结果继续或呈现最终摘要。** 门禁未过时，汇报已确认部分、本轮复核结果与开放项；当前用户能回答的直接追问，待 BA 决定的给出待审阅问卷，缺资料的注明影响与来源，不请求定稿批准。门禁全过后，向用户展示：目标、范围内、范围外、AC 列表、关键决议、明确按推荐通过的题、风险及收敛依据；标明"已收敛待批准"，然后**结束本轮**。不要把生成对齐文档称为对齐完成，也不要在同一条回复里开始制定开发计划或写代码。
6. **等待明确批准。** 只有用户在**后续一条新消息**里明确批准这份摘要（例如"对齐通过"），才把 `stage` 改为 `planning`，并在文档"批准记录"写上批准人、日期与原话。用户最初"帮我做这张卡"的请求、建卡目录时的同意、"没问题的话就……"这类条件句，都不算批准。对齐批准只放行 04 制定开发计划，不是开发许可。
7. **收尾。** 按 `session-protocol.md` 打印下一步（下一个窗口：`dev-plan`，建议顶级模型），结束本轮。不要在本窗口开始制定开发计划，也不要建分支、写代码。
8. 批准后若对齐文档有实质修改，或出现影响原结论的关键新问题，按需回到 `clarifying` 或 `aligning`，注明原批准不覆盖哪些变更；重新复核收敛门禁并走 5–6。重新批准时，原批准记录标"已被 <日期> 修订取代"，新记录带修订版本（如 03 v2），下游引用批准写明版本。

## 本轮复核结果

每批答复后，按 02 的"每轮答复后的复核"主动检查，并把以下结果简要写入 `02-questions.md` 的轮次记录，在回复中呈现。不能只写"已检查，无新问题"或勾选完成：

- **依赖展开**：本轮哪些 Q 或技术前置已明确，解锁了哪些后续 Q；哪些待细化领域已可展开，哪些移出范围、哪些仍受前置问题或资料阻塞。
- **场景与冲突**：根据本卡相关的正常流程、权限、异常、历史数据与上下游场景推演答复的后果，说明检查了哪些边界，发现什么缺口；与原卡、旧决议、术语和已核实技术约束核对。不相关项可说明不适用，不为凑数增加问题。
- **验收覆盖**：本轮新增或变化的范围、规则与场景由哪些 AC 覆盖；受未答题或冲突影响的 AC 标为草稿，缺少可观察验收结果时形成追问。宣称收敛前，再交叉核对整卡的范围、业务规则与 AC，检查是否还有从未列入问卷的关键取舍。
- **本轮判断**：继续追问（列出当前可问的 Q）、等待有权者答复或缺失资料（列出 Q / 缺口与影响），或已收敛待批准（说明上述检查为何没有留下关键开放项）。不同类型的开放项可以并存；能继续处理的部分先处理。

没有新问题可以收敛，但必须有复核依据；当前没有可立即提问的问题时，仍要核对被资料阻塞的题和待细化领域，有待展开关键题、关键冲突或影响范围与 AC 的缺口时不能收敛。新增问题按 02 的目标与边界筛选，范围外建议不自动变成本卡阻塞项。复核依据同步引用到 `03-alignment.md`，不重复抄写答复。

## 完成标准

- `03-alignment.md` 无"待定"，AC 有编号且可测。
- 最近一轮的复核依据已落档并向用户呈现，没有待展开关键题或关键缺口。
- "批准记录"段有批准人、日期与原话。
- `stage: planning`。

## 常见错误

- 把 BA 的一句"可以""按建议来"当成对所有问题的答复。阻塞题逐题要答复，没答的继续追问。
- 当前列表答满就请求批准，没有复核待展开题、新增场景和受影响的 AC。
- 发现新问题后只提示用户输入 `clarify`，或仅写"无新问题"却不给复核依据。
- AC 写成"实现 XX 功能"。AC 必须是用户或系统可观察的行为。
- 批准前顺手改了代码。对齐阶段不碰业务代码。
- 把对齐批准当成开发许可，在同一窗口接着写开发计划、建分支或写代码。对齐批准只放行 04，04 在新窗口进行。
