# 02 · 拆问题（Clarify）

先围绕 `01-card.md` 与 Dev 交互澄清，再把需要 BA 决定的部分整理成本轮问卷，并附上对需求合理性与用户价值的质疑。产物是持续维护的 `02-questions.md`，按 `.ai/templates/card-analysis.md` 第二、三部分填写。

本阶段可以与 03 对齐在同一个窗口完成：问卷发给 BA、答复回来后，用户在同一窗口输入 `align` 即可；答复隔天才到就新开窗口。

## 默认先交互，再整理问卷

- **默认交互式（grill）**：先与用户（通常是 Dev）按"设计树"分轮澄清。第一轮先问范围题；每轮把前置条件已满足的问题编号一起列出，附有依据的推荐，答完后按下文复核，再决定下一轮问什么。代码事实由 AI 自己查。
- **文档式（questionnaire）**：用户明确要求直接出问卷、离线整理或跳过访谈时，直接整理本轮问卷草稿，仍保留问题依赖和后续轮次。要拿去问 BA 也可以先交互；不要仅因收件人是 BA 就跳过 Dev 澄清。

Dev 已明确不知道或无权决定的题，标为待 BA 决定，不反复要求 Dev 代答。Dev 的业务意见只有在其有权决定时才记为决议，否则保留为建议。没有需要 Dev 澄清的内容时，可以直接整理问卷，说明依据，不为凑轮次制造问题。

交互过程中逐轮写入 `02-questions.md`，保留原话、来源、当前理解和待确认项，不等访谈结束才落档。范围、口径、做法类答复先回述一句理解；确认前保存为待澄清，不能记成已确认结论。

**整理 BA 问卷的时机**：当前能向 Dev 查清的内容已处理，剩余待 BA 决策及其依赖已列清。此时即可整理本轮问卷，不要求先拿到 BA 的全部答案；依赖 BA 前置决定的细节留待下一轮。

## 提问前的证据工作

每个问题在写下之前先问自己：代码能回答吗？

- 能：去查，把答案和证据路径写进 `01-card.md` 的核实段，不进问卷。
- 不能，但对端仓库或上下游文档能回答：按 `missing-context.md` 处理。
- 只有 BA 能回答（产品意图、范围、优先级、用户习惯、业务规则的取舍）：进问卷。

代码能说明**现状与技术约束**，不能代替**产品决定**。"现有功能是这么做的"只能作为推荐答案的理由，不能据此认定 BA 也要这样、从而不问。

## 先定范围，再展开（借自 wayfinder / grilling）

范围决定其他问题问不问。问卷分两层：

1. **范围题**放在最前面，单独一组：本卡交付到哪一步、哪些明确不做、和相邻卡或后续卡的边界。01 已固定分期词表时，范围题直接引用代号（"本期 A 是否包含 X"），不重新解释代号。
2. **其余问题**逐题标"依赖"：答案会因范围题而作废或改变的，写"依赖：Q1"。

范围题还没有答复、而且依赖它的问题很多时，本轮只展开范围题和不依赖范围的问题，其余列进"范围确认后再问"一节（只写一句话标题，预留 Q 编号并标性质、依赖），答完范围再展开成下一轮。问卷顶部写明轮次，不要把后来想到的问题零散地追加到末尾。

## 每轮答复后的复核

收到一批答复后，无论来自 Dev 还是 BA，都做一次复核；不是填完答题框就结束：

1. **保留答复并核对权限。** 原话、答复人、来源与当前理解分开记录；含糊、冲突或无权决定的答复仍是待澄清。
2. **重算依赖。** 前置决定明确后，展开仍在范围内的后续题；被排除的题标"本期不适用"并引用依据，不删除记录。
3. **检查新缺口。** 按本卡相关的问题分组复核：是否出现新场景、术语或规则冲突、权限或异常边界、历史数据与上下游影响、验收缺口；需要查证的技术事实回到证据工作，业务取舍形成问题。已有明确依据的内容不重复问。
4. **决定继续问谁。** Dev 能回答且有权决定的继续交互；待 BA 决定的整理进本轮问卷；依赖未定的列入待展开项。复核后把已识别且可展开的问题整理齐，再交 Dev 审阅，不能因为用户答完了当前列表就宣称全部问题已收敛。

Q 编号跨轮唯一、不重排、不复用，新题从已有最大编号递增。重开旧题时保留原答复与原因；建议、范围或验收变化时核对受影响的 Q 和 AC，不能沿用已失效的结论。每轮在问卷记录复核范围、变化、新增或待展开的 Q 编号及下一步；无需为检查项额外制造问题。

## 术语（借自 domain-modeling）

卡里模糊或一词多义的词单独成节，放在范围题之后，例如"请求次数""总费用""月均""对齐"。每个词写：

- 候选含义（两到三个），各自对照代码、接口实测或数据说明"现在系统里这个词指什么"。
- 推荐含义，以及选别的会改变什么。

先查 `spec/domain.md` 的术语表，已定义的词直接引用，不再问；卡里的用法和术语表冲突时，把冲突当成一个问题问。

## 问题分组（按需取用，空的组删掉）

1. 范围边界：本卡交付到哪一步、哪些场景在内、哪些明确不做、和现有功能与后续卡的边界（放最前，见"先定范围"）。
2. 业务目标与用户价值：谁用、解决什么问题、不做会怎样、怎么衡量做成了。
3. 数据与状态：新字段的来源与含义、状态迁移、历史数据怎么处理、唯一性与幂等。
4. 交互与展示：入口、筛选、排序、空态、错误提示、权限。
5. 上下游影响：对照 `context/upstream-downstream.md`，涉及的系统各问一遍"对方行为是否变化、失败怎么办、是否要通知对方"。
6. 验收标准：把 BA 给的验收标准改写成 Given / When / Then 草稿，让 BA 确认或修正。
7. 非功能：灰度与白名单、幂等与重复提交、时区、日志与可追溯、并发、超时与重试。
8. 兼容与迁移：表结构变更、配置键新增、老数据回填、发布顺序（先测试环境后生产）。

## 每个问题的格式

```
### Q3 · 已归档任务是否继续发送提醒（虚构示例）
_为什么问_：示例代码能读取任务归档状态，但提醒流程尚未按该状态过滤；实际使用时应替换为本卡的真实证据。
_影响_：决定哪些任务仍需要提醒；历史待发送提醒是否处理，另列问题确认。
_性质_：阻塞　_依赖_：无
_建议_：已归档任务停止发送提醒，仍由有权者确认。
> 答：
```

一题一意，不写复合问题；最重要的放前面；每题给有依据的推荐，信息不足时写清缺什么，不编造建议。答复后补状态（待答 / 已答 / 按建议 / 待澄清 / 本期不适用）、答复来源与当前理解。

**推荐不等于默认**（借自 Trellis）。每题标性质：

- **阻塞**：范围、费用或数据口径、AC、不可逆的选择。必须逐题有明确答复；BA 笼统回一句"按建议来"不算答复这类题。
- **可默认**：影响小、以后能改的细节。有权答复者明确同意采用这些题的建议后才通过，并保留当时接受的建议；未答仍是未答，沉默不算接受。

## 发给 BA 之前，先和 Dev 过一遍（借自 to-questionnaire）

交互中已收敛的内容带入问卷，本轮待 BA 问题整理好后，再给用户（Dev）审阅。直接文档式也先作为草稿呈现：

1. **Dev 能答的**：Dev 了解业务且有权决定的题，答案写进答题框并注明"Dev 答"，不再发给 BA；仅有建议的题仍需有权者决定。已有明确答复不重新问。
2. **这次最要拿回什么**：请 Dev 确认本轮必须拿到结论的问题，排在最前面。
3. **收件人**：确认发给谁（BA、业务方、上下游负责人）；不同收件人的问题可以拆成两份问卷。

按 Dev 的意见精简后，才算可以发出的本轮问卷。保留已答题的记录，待答部分按收件人组织；问卷由用户转发，不自动发送。交互进行中或草稿尚待 Dev 审阅时，`stage` 保持 `clarifying`；本轮审阅完成后才改为 `aligning`。

## 价值质疑（必写，哪怕结论是"没有异议"）

对卡的合理性做独立判断，写在问卷末尾的"质疑"段。每条质疑包含：

- 质疑点：哪部分不合理，或对用户没有价值。
- 证据：代码、数据、历史卡、`decisions/rejected/` 里的先例。
- 替代方案：更小、更简单或已有功能能覆盖的做法。
- 严重度：阻塞（不解决不该进入开发）/ 建议（可以先做再改）/ 备注。

质疑是给 BA 决策用的，不是 AI 替 BA 决定。需要决定的质疑纳入正式 Q 编号，关键质疑标为阻塞，不能只留在末尾无人答。BA 否决质疑后，把结论记进 `03-alignment.md` 的"被否决的质疑"，并视情况写入 `decisions/rejected/`。

## 完成标准

- 问卷里没有一条问题是代码能回答的。
- 范围题在最前面；其余每题都标明性质（阻塞 / 可默认）与依赖。
- 模糊术语已列入"术语"一节，或确认没有。
- 已与 Dev 澄清并审阅本轮问卷；有权 Dev 的答复已注明，无权决定或不知道的题已转为待 BA 决定。直接文档式不虚构访谈或审阅记录。
- 已做本轮复核，新问题、待展开项、冲突及依赖均有记录；产出问卷不表示 BA 问答已收敛。
- 每题有"为什么问、影响、性质、依赖、建议"。
- 质疑段存在，每条有证据与替代方案。
- `README.md` 的 `stage` 为 `aligning`。
- 已按 `session-protocol.md` 收尾：需要人做的事是把问卷发给 BA，下一个窗口是 `align`。
