# 02 · 与 Dev 沿设计树澄清（Clarify）

围绕本卡与 Dev 讨论目标、流程、边界和关键取舍，形成共同理解。BA 问卷是需要业务判断时的按需产物。输入为 `01-card.md`、已有讨论和相关项目资料；按 `.ai/templates/card-analysis.md` 第二部分维护 `02-questions.md`，有价值疑点时使用第三部分。对端资料缺失按 [缺上下文协议](missing-context.md) 处理。

## 从已有依据出发

- 先读原卡、AC、相关代码和已有结论，简述当前理解与真正的缺口。明确的原卡要求直接沿用；没有具体冲突或变更时，不重复询问“这些 AC 是否都要做”，也不因答复者是 Dev 就要求 BA 再确认一次。
- 代码、配置、文档能回答的事实由 AI 查证，证据放在 `01-card.md`。代码说明现状，不能覆盖原卡期望；Dev 提供的新进度或设计作为输入，必要时核对相关实现，不把旧卡状态当成当前事实的唯一依据。
- Dev 是主要讨论者：需求理解、流程推演、技术选择和关键约束都可以讨论。只有会影响需求理解或可行性的技术问题需要在这里收敛；一般实现细节留给后续开发，不在澄清阶段完成整份技术设计。

## 按设计树推进（参考 grilling）

1. **找当前可讨论的问题。** 从已有目标与范围向下展开，每轮一起提出前置已明确的独立问题，编号并给出建议、理由和主要取舍。范围不清才先问范围；已有答案直接引用。一题的答案依赖本轮另一题时，放到下一轮。
2. **先与 Dev 讨论。** 等待答复后更新理解，再展开被解锁的分支。对含糊或冲突之处，用具体场景追问；明确答复直接记录，不要求每答一题都再回述确认一次。
3. **未知项先分清性质。** 能查的继续查；缺少资料的写清查什么、由 AI / Dev / 哪位技术负责人补齐。Dev 暂时拿捏不准时，先一起找证据、比较方案。只有确实涉及业务意图、规则或范围取舍，才转为待 BA 判断；“Dev 不知道”本身不是转交理由。
4. **按影响复核。** 答复是否解锁下一分支、与原卡或已知约束冲突、影响相关正常 / 异常场景及 AC？只检查本卡相关部分，并简述变化与下一步。技术前置未明只阻塞依赖它的分支，其余继续。

先核实场景是否成立，再讨论该场景下怎么办。例如先查清“成功后数据是否可能变化”，再讨论更新或替换；已经有依据排除的分支注明理由即可。尚无法提问的范围内事项，简记前置与重访条件，不提前编出整套问题。额外能力留作后续建议，不自动变成本卡阻塞项。

## 何时找 BA

原卡存在业务歧义或冲突、需要新增 / 改变业务规则、范围、权限或验收，或技术限制迫使产品目标取舍时，先与 Dev 梳理清楚，再提炼需要 BA 决定的部分。Dev 在既定要求内的技术决定直接记录；Dev 转述既有业务结论按实际来源记录；新的业务取舍若超出其职责，保留为建议并找相应业务负责人。

给 BA 的每题只需要：**已知背景与具体分歧、影响、建议及理由、要决定的一点、答复位置**。依赖未明的细节暂不展开；只发送待决定的部分，不要求 BA 重答 Dev 已查清或原卡已写明的内容。草稿先给 Dev 审阅，由用户自行转发，不自动发送；可在其他独立分支仍推进时整理必要的业务问题。

若没有需要业务判断的缺口，直接在 Dev 侧完成澄清，无需生成 BA 问卷。用户明确要求直接出问卷时可跳过交互，仍只保留真正的业务问题，技术待查另记；明确要求暂停时保存当前进度。

## 轻量记录

- `02-questions.md` 只保留当前共识、关键讨论与依据、待查 / 待展开项，以及按需出现的 BA 问题。删除空节，简单卡可以只有几条记录，不要求每轮填完整复核表。
- Q 编号跨轮保留；结论写清来源，关键原话与实质修订保留。相同来源可按一批记录，相关 Q 引用对应批次并保留旧来源，不重复填姓名、身份、日期；未提供的信息不补造。仅在问题已转发且内容实质变化时保留所发版本，异步答复核对当时题干与建议。
- 推荐尚未接受时仍是建议；明确“按建议”且对应内容唯一时可记录接受的结论，存在多种理解才追问。关键业务取舍不能由沉默或 AI 推断代替。技术后续项由 Dev 评估影响；业务项延期或移出范围由相应业务负责人决定，保留依据和后续处理。
- 发现具体价值疑点时给证据、影响与更小替代方案，先与 Dev 讨论；需要改变业务目标时再提给 BA。没有疑点无需写“无异议”，也不为模板制造质疑。

## 收敛与下一步

目标、范围、关键规则和可观察 AC 已清楚，没有影响这些判断的未解问题或技术前置时即可收敛；当前无题可问但仍有关键依赖时不能结束。无需穷举范围外分支，也不要求所有实现细节提前确定。

讨论、查证或业务问题草稿审阅中保持 `clarifying`。本轮澄清已收敛、准备整理结论，或已审阅的业务问题正在等待答复且当前无可继续的 Dev 讨论时，记为 `aligning`，README 写实际下一步；创建问题文件本身不改变状态。

首次整理最终对齐文档由用户启动 `align`，不以存在 BA 问卷或 BA 答复为前提。已经在 `align` 循环内时，直接继续整理结论或按设计树讨论，无需切换命令。完整流程的最终对齐批准按 [03 对齐](03-align.md) 执行，不在逐题答复后增加审批。按 [会话协议](session-protocol.md) 保存进度并简述已对齐什么、还缺什么、下一步由谁处理；详细实现留给 04 开发计划。
