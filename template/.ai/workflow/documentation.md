# 项目文档维护

读取项目知识时发现冲突，或本卡改变实体、接口、配置、架构、上下游行为、工程约定时，按本说明维护文档。规范以当前可用的知识为入口，卡片保存目标与实施过程，历史通过指针追溯。

## 信息放在哪里

| 信息 | 定义位置 | 更新方式 |
|---|---|---|
| 当前代码结构、领域语义、已实现行为 | `spec/` 对应主题 | 按代码与验证证据改写现行段落，替换已失效内容 |
| 当前工程约定与必须遵守的约束 | `spec/conventions.md` 等；有实质取舍时引用有效 ADR | 记录约定依据；历史代码偏离时标明现状和差距，不把旧实现自动变成规范 |
| 当前对端、上下游事实和共享契约 | `context/` 对应主题 | 指定主维护位置；其他文件引用，跨仓库镜像记录同一契约修订 |
| 本卡希望实现的行为、尚未实施的方案 | 完整流程用 `03-alignment.md`、`04-dev-plan.md`；轻量用 `maintenance.md` | 保留相应批准 / 本次授权及范围；实现后的长期结论写回现行文档 |
| 原答复、旧方案、验证过程、被替代的结论 | 卡内 `02` / `05` / `maintenance.md` / `research/history/`、journal、Git 历史 | 保留原有依据，注明已被何处取代；现行正文只留必要指针 |

每个主题选一个主定义位置，其他文档引用它。更新现行正文时，同时查找引用旧实体、路径、字段、配置或术语的相关项目文档，修正受本卡影响的引用。有效 ADR 与历史包袱保留状态和适用范围；ADR 的替代按 `decisions/README.md` 处理。

## 写什么，哪些改用指针

- 长期正文重点写语义、职责边界、取舍原因、不成文约定、容易误用的约束，以及典型实现入口。阅读路由按 [规范索引](../spec/index.md#阅读指针怎么写) 组织。
- 完整接口列表、字段定义、依赖版本、测试数量等可从代码或工具低成本查询的信息，优先引用其主来源或查询方法，避免手工维护第二份清单。保留理解行为所必需的字段语义、兼容要求和状态约束；来源可查不表示这些解释可以省略。
- 确需保留数字或清单作为验收 / 排障证据时，标注统计口径、日期、适用修订和来源，将完整快照放卡内证据，长期正文只留结论与指针。测试文件数、测试类数与实际执行用例数分别说明。
- 卡 README 只保留 [当前恢复摘要](../cards/README.md#当前恢复摘要)，过程保存在阶段产物或历史记录；journal 的分卷、索引与提炼按 [日志规则](../journal/README.md)，不另建重复状态台账。

## 现行信息和证据

- **先标清适用范围。** 文档描述哪个仓库 / 版本的实现，还是哪个环境的已验证行为。已批准、代码已实现、已部署、环境已验证分别记；没有部署证据就写“部署状态未核实”。
- **同一主题只保留一份现行说明。** 改动后直接修订对应段落；旧口径移到历史记录并注明替代关系，不连续追加多段都叫“当前行为”的说明。确有多个受支持版本时，明确区分版本和调用方。
- **高变动事实带核实记录。** 实体、接口、配置、调度、上下游行为的变更，在相关章节记录核实日期、来源路径 / 符号、实现修订和验证证据。未提交内容标“工作树未提交”，提交后由卡内提交记录关联；不预填未来提交号。稳定术语和规则可复用已有决策指针，不要求每段都填表。
- **保留必要证据即可。** 长期文档只留结论和可追溯位置；完整响应、日志、讨论放卡内。事实样例须脱敏，内部材料保留在项目仓库，对外模板只使用通用说明或虚构示例。

记录格式（按主题填写，不复制为每个文件的空表）：

```text
核实：<日期>；实现依据：<仓库修订或工作树未提交>，<路径#符号>
验证：<测试/实测证据路径及覆盖范围>；部署/环境验证：<证据或未核实>
历史：<被替代记录的链接；没有则省略>
```

**遇到冲突时按问题类型处理：**

1. “现在怎么运行”查当前代码、配置和实际执行证据；“应该怎么运行”查有效验收依据及工程约定，完整流程核对 03/04 批准，轻量核对维护记录引用的既定行为与本次授权。代码现状不自动推翻已批准需求，计划也不能证明功能已实现。
2. 只是文档过期且证据明确，修订当前事实并保留必要历史；涉及范围、AC 或设计取舍，按原阶段的变更规则处理。执行者将冲突交给协调者，不自行扩展可改文件。
3. 仍无法确定时，记录冲突双方、适用修订、影响和待核实项；暂停依赖该结论的工作，继续独立部分。文件较新、索引标“完成”都不足以解决事实冲突。

## 随开发维护

下列 04–07 分工用于完整流程；轻量维护由本次维护者在 `maintenance.md` 记录文档影响、更新证据与评审结论，同样在已验证实现后及时回写、评审前完成，相关文件无需更新时注明原因。轻量升级后转到完整计划清单，原记录保留为历史指针。

1. **04 计划：列出文档影响。** 使用计划模板的清单，为每个受影响主题指定文件 / 章节、变更原因、维护者与更新时间。没有影响时写“无需更新”及原因。此时拟变更的契约仍属于计划，不提前覆盖现行事实。
2. **05 开发：随已验证实现写回。** 每批实现集成后，由协调者按清单更新已变化的事实并补证据，最迟在卡级评审前完成。实施中发现遗漏的文档影响，补充清单与开发记录；若改变设计或范围，仍走原变更规则。共享文档默认由协调者统一维护；专门的文档子任务须列明可改文件，避免多人并改。
3. **05 评审：核对文档和实现。** 评审清单内的文档变更及受影响的现行说明；检验是否仍引用旧口径、是否把未实施方案写成事实、镜像是否同版。记录完成结果或“无需更新”的依据；已实现行为的文档遗漏属于必改项。
4. **06 DC：核对验证范围。** 本地实现已验证但未部署时，文档写明这个边界；环境验证有新结果时补证据。缺少必需的验收证据仍按 DC 门禁处理。
5. **07 结卡：提炼与收尾。** 复核开发期间的文档更新，并提炼可复用教训、术语、决策和遗留问题。QA 引起的新变化同样随修复更新，不把日常事实更新都留到结卡。

清单状态：**待更新 / 已更新 / 无需更新（原因）**。只有现行说明已准确反映实现及验证范围，才能记“已更新”；“未部署 / 待环境验证”是验证范围，不代替完成文档更新。完整流程的清单状态与证据统一回填 `04-dev-plan.md`，`05-dev-log.md` 只引用清单及记录偏差；轻量统一回填 `maintenance.md`，不再维护第二份状态表。

## 跨仓库契约

- 在 `context/api-contract.md` 标明主维护仓库与文件、契约修订、核实依据；镜像复制同一正文和修订。`related-projects.md` 只指向它。
- 计划中的契约变更先在 04 共同契约确定。实现后更新主文档和镜像，各端的实施 / 验证状态分别列明；镜像已更新不表示客户端已经实现或部署。
- 对端未就绪或不可访问时记录缺口、责任方和跟进任务。若本卡承诺双端交付，缺口仍阻塞完成；若已批准分批交付，在现行契约写清版本边界与兼容方式。不能靠补一份镜像掩盖未完成的交付。

## 文档检查

接入、升级及本卡文档发生变化时，对相关范围逐项人工核对；可用现有检索、差异和测试命令辅助，不要求新增脚本。结果写入已有的接入 / 升级记录、04 文档清单、维护记录或评审记录，无需单独建报告。

1. **路径与符号。** Markdown 相对链接从所在文档解析；源码引用从注明的仓库根目录解析。核对完整路径和实际类 / 方法，不能以别处存在同名文件判定有效；行号变化后重新定位符号。
2. **章节与移动。** 打开链接检查锚点确实对应目标内容，重复标题要确认具体位置。改标题、移动文件、卡片归档或整理历史后，更新现行入口与受影响的引用；历史中的原始定位保留来源修订，必要时补新位置指针。
3. **入口与镜像。** 核对 `AGENTS.md`、`CLAUDE.md` 到流程的导航，以及本基线 `.agents` / `.claude` 对应阶段 skill 的一致性。共享契约核对主来源、修订和约定镜像正文；各仓库实施 / 验证状态分别保留。对端不可访问时记录待核实范围，不能宣称镜像检查通过。
4. **占位与未知。** 公共模板骨架和产物模板允许保留明确占位；已接入项目的入口、有效规范与实际卡产物必须填入真实内容或写明不适用及原因。缺少必要事实要记录“未核实”、影响和后续处理，不通过删除章节或伪造内容消除占位。不能仅凭搜索命中模板中的 `TODO` 或 `<...>` 判定接入失败。
5. **语义与重复。** 核对现行结论与本次实现、测试或实测证据的关系，是否遗漏边界或重复维护可查询清单。路径、章节或镜像一致只证明结构可用，不能证明业务行为正确；尚无条件验证的范围照实记录。
6. **公开范围。** 只将通用规则或明确标记的虚构示例带回公共基线；检查改动与待发布历史中的内部标识、路径、地址、业务数据和凭证。真实证据保留在原项目受控位置。
