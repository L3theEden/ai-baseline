# 04 · 制定开发计划（Dev Plan）

在一个新窗口里，用顶级模型把已批准的 `03-alignment.md` 变成一份可评审的技术设计，再把实现拆成执行者（可以是低端模型）能独立完成的子任务单。产物：`04-dev-plan.md`（模板 `.ai/templates/dev-plan.md`）与 `tasks/T<nn>-<slug>.md`（模板 `.ai/templates/subtask.md`）。

本阶段**不写业务代码、不写迁移脚本、不建分支**。可以读代码、跑只读命令、对外部接口做只读实测（结果写进 `research/`）。

## 进入条件

- 卡目录 `README.md` 的 `stage: planning`，且 `03-alignment.md` 的"批准记录"有批准人、日期、原话。不满足就停，提示用户回到 03。
- 已按 `session-protocol.md` 开场（`git pull` 到最新）。

## 两道确认，同一个窗口

1. **设计确认**：完成步骤 1 到 6 后呈现设计摘要，停下等用户回复。
2. **拆解确认**：设计确认后完成步骤 7 到 10，呈现拆解摘要，停下等用户回复"计划通过"。

两道确认都必须是 AI 呈现摘要**之后**用户的一条新消息。用户对设计提出修改，就改完再呈现一次，直到确认。拆解确认后才把 `stage` 改为 `ready-for-dev`。

## 步骤

### 1. 现状勘察

- 按 `spec/index.md` 的任务类型读规范，读过的文件记进计划"开发前已读"。
- 找到本卡要改的代码路径和同类功能的现有实现（可以照抄的模式），每条写"文件:行号"证据。
- 查最新迁移版本号和相关模块最近的提交（`git log --oneline -15 -- <路径>`）。主分支上多人并行加迁移，版本号容易撞。
- 涉及外部系统（第三方 API、对端仓库、数仓）的卡必须做只读实测与对端代码核实，结论写进 `research/<主题>.md`，真实响应样例原样保存，后面做测试夹具；当下拿不到实测条件的，列入「外部事实与未知项」（见步骤 3）。

### 2. 方案选型

- **先过存在性门，再选型**：每个新表、新字段、新状态、新配置键、新依赖，先答"不做会怎样"（对应 `spec/conventions.md`「最小实现阶梯」第 1–2 级与「设计默认值」）；答不上来的删掉，或写进"明确不做"。结论写进方案选型记录与「一页看懂」的"本次砍掉的候选"。
- 每个关键技术问题至少列两种做法，写清取舍并给出推荐。典型问题：数据怎么存、放在哪一层、同步还是异步、依赖谁的数据、要不要直连他人的数据库、失败时整体回滚还是部分保留。
- 技术取舍由 Dev（用户）拍板：一次只问一个问题，附推荐和不选它的代价；代码能回答的事实不问。
- 产品意图、范围、验收口径的问题不在这里决定：退回 03 与 BA 对齐，不在计划里私改 AC。

### 3. 技术设计

先判断卡的复杂度，写进计划开头：

- **轻量卡**：改动集中在少数文件，没有新表、新外部集成、新定时任务、不可逆变更。只写"改动边界"：最小行为差、行为真正所在的位置、改哪些文件、明确不做什么。
- **复杂卡**：命中任一项即是：新表或改表、新外部集成、新定时任务、状态机、跨仓库、不可逆变更。下列各节必填，不适用写"无"并说明原因。各节深度与后果相称：命中不可逆变更、财务金额、对外系统写入、多副本并发之一的卡是重档，各节写全；其余复杂卡每节先过存在性门，不为填模板造设计。
  - **模块边界与调用链**：入口、编排、协议、存储各归哪个类或包。
  - **数据模型**：每张表的列、类型、约束、索引、外键、量级与增长、保留期；迁移脚本版本号（预占）。
  - **状态机、幂等与事务**：状态与迁移条件、幂等键、重复执行的语义、事务边界，以及 flush 顺序、唯一索引冲突这类并发陷阱。
  - **接口契约**：外部接口（鉴权、分页、限流、字段实测样例）、管理端接口（路径、参数、返回、权限）、前后端契约变化。
  - **失败模式与容量**：超时、重试上限与退避、部分失败、限流、数据量与内存估算、多副本并发（分布式锁）、时区边界。
  - **配置与安全**：新配置键与默认值、ConfigMap / Secret、开关默认值、日志前缀与脱敏。

涉及外部系统（第三方 API、对端仓库、数仓）的卡，无论轻重都必填**外部事实与未知项**一节：已核实的事实（真实响应、分页、时区、错误码，指向 `research/`）逐条列出；未核实项要么阻塞设计确认，要么在摘要里显式标注"此项未定，设计可能重做"。

无论轻量卡还是复杂卡，计划开头都必须有**「一页看懂」**一节：数据流图（上游 → 步骤与阻断分支 → 落地 → 消费方，一屏）、本次要 Dev 拍板的取舍 3–5 条、明确不做、验收锚点。它是计划的人读层，也是呈现设计摘要的载体，批准后原样留档。

### 4. 契约

把所有子任务都要遵守的东西只定义一次：表结构要点、实体与 DTO / VO 字段名、公共方法签名、配置键、日志前缀、错误码。子任务单引用这里，不各写一份。多个执行者分头写代码还能拼得上，靠的就是这一节。

### 5. AC 追踪

建表：AC、设计要素、测试用例、子任务。

- 每张表、每个接口、每个配置键、每个定时任务都要能追溯到某条 AC。追溯不到的删掉，或者标为"超出本卡"写进范围外。
- 某条 AC 没有设计要素或没有测试覆盖，计划就不完整。

### 6. 测试设计

- **约定测试缝**：在哪个公共接口上测（Service 公共方法、Controller、client 边界）。在这里就和用户确认，执行阶段不再现场决定。
- **每条 AC 列出用例**：输入与期望值。期望值来自规格或真实样例，不从实现推导。
- **解析 / 匹配 / 编码 / 时区类改动**：用例必须覆盖特殊字符（`+`、空格、大小写、Unicode）与边界值。
- **测试夹具**：外部接口用 `research/` 里保存的真实响应，不手写想象中的响应。
- **只能在 dev 验证的项**：例如迁移脚本在 PostgreSQL 上执行、真实密钥调用，写明验证方式。

然后呈现**设计摘要**：以计划的「一页看懂」为主（数据流图、要拍的取舍、砍掉的候选、明确不做、验收锚点），再补 AC 追踪有无缺口、测试缝、主要风险；摘要即计划里那一节，随计划留档。停下，等设计确认。

### 7. 拆子任务

先判断拆不拆：

- **不拆**：轻量卡，或者强耦合、拆开反而要大量协调的卡。计划写明"不拆"和理由，整张卡作为一个子任务 T01；跨仓库的卡不拆时也按仓库分，每个仓库一个子任务（如 T01 后端、T02 前端），因为一张子任务单只有一个工作目录。
- **拆**：按下列规则拆成子任务单，每个子任务一个文件：`tasks/T01-<slug>.md`、`tasks/T02-<slug>.md` 等。

拆分规则：

- **一个子任务只交付一个可验证的行为。** 改动文件少（建议含测试不超过 6 个），一个新窗口能做完，有一条能变红也能变绿的验证命令。
- **先契约后实现。** 共享的迁移脚本、实体、Repository、接口签名、测试夹具放在第一批，后面的子任务都建在契约之上。
- **标依赖与批次。** 写明"依赖：T01"。同一批次的子任务互不依赖，**改动文件不重叠**，这是并行的前提。
- **标执行者建议。** 涉及事务、并发、幂等、状态机、外部接口异常分支、安全与鉴权的子任务，默认标"需顶级模型"。实体、VO、配置、部署模板、简单映射这类机械性子任务标"低端模型可做"。
- **前后端分开拆。** 一张子任务单只写一个工作目录。另一仓库的子任务单也放在本卡目录，工作目录写另一仓库；两个仓库的子任务依赖的契约已在第一批或计划里定好时，天然可以并行。
- **fix 卡先复现。** 第一个子任务是写出能在该 bug 上变红的测试（见下文"fix 卡的反馈回路"），后面的子任务才修。
- **子任务只是卡内步骤，不是新卡。** 拆下来发现一张卡装着两个能独立交付的需求，把"建议 BA 拆卡"写进计划，由用户去和 BA 确认。
- **外部依赖单列。** 依赖外部资料、他方交付或未定契约的子任务不排进并行批次，单列"阻塞候选"，写明解除条件与解除后的执行顺序（关键路径）；解除前不派发。

### 8. 写子任务单

按 `templates/subtask.md` 写全每一节：目标、对应 AC、依赖与批次、执行者建议、工作目录、可改文件清单、契约引用与签名、先读（至多 3 份规范、1 处参照实现的文件行号、测试夹具）、先写的测试（用例表）、验证命令、完成标准、何时停下。

**写给一个没看过本窗口任何对话的执行者。** 它只读这张单子和单子里列出的文件。单子里不能出现"参照上文""按刚才讨论的"这类说法。

### 9. 预演

挑一两张最容易有歧义的单子（通常是第一批的单子，以及标"低端模型可做"的核心单子），做一次**只读预演**：派一个低端模型子代理，或请用户开一个新窗口，让执行者读完单子后说出"会改哪些文件、每个文件改什么、先写哪些测试、跑什么命令"，不改任何文件。说法和计划对不上的地方，就是单子写得不清楚的地方；改好单子再预演一次。

### 10. 单向门、发布与回滚

- **不可回头的点**：推到远端主分支会触发 dev 部署；迁移脚本一旦在 dev 执行就只能新增、不能再改；对外部系统的写入。
- **迁移版本号**：在计划里预占，执行前和推送前各核对一次。
- **推送时机**：本卡提交在卡级代码评审（`05-card-review.md`）通过后才推送；需要提前推送做 dev 联调的，在计划里写明原因和范围，由用户确认。
- **部署前置**：ConfigMap / Secret 新键（部署平台预建）、开关默认值、发布顺序、发布后的手动操作。
- **回滚步骤**。

然后做一次**独立审查**：派一个只读子代理，或请用户开一个新窗口，只给它 `03-alignment.md`、`04-dev-plan.md`、`tasks/` 和 `spec/index.md` 的路径，按六个问题审：AC 是否全覆盖、有没有追溯不到 AC 的东西、单向门是否都识别了、子任务单能否独立执行、每个新表 / 字段 / 状态 / 配置键能不能删（存在性门的复核）、外部依赖子任务是否都有解除条件。把发现的问题修掉。

最后呈现**拆解摘要**：子任务表（编号、目标、批次、依赖、执行者建议、工作目录）、并行方案、单向门、预演与审查结论。停下，等用户回复"计划通过"。

## 批准之后

1. 在 `04-dev-plan.md` 的"批准记录"写批准人、日期、原话。
2. `README.md` 改为 `stage: ready-for-dev`。
3. 按 `session-protocol.md` 收尾：下一个窗口是 `develop`，建议顶级模型。**不要在本窗口开始派发或写代码。**

## 批准后的变更

- 执行中发现设计要改（新表或字段、新接口、新依赖、新配置、范围变大）：执行者停下记进子任务单，协调窗口记进 `05-dev-log.md` 的偏差段。属于实质变更就把 `stage` 改回 `planning`，在新窗口修改计划并重新确认。重新确认后，原批准记录标"已被 <日期> 修订取代"，新记录带修订版本（v2、v3…）；05 与卡级评审引用批准时写明版本。
- 只改子任务单的措辞或拆分方式，不动设计和 AC：协调窗口可以直接改，记进偏差段并告知用户。
- 用户显式授权"直接同步改"时，可在当前窗口改 03/04 并记录授权原话与变更摘要（进批准记录），不必新窗口重走；AC 或范围变化仍回 03 修订并重新批准。

## fix 卡的反馈回路

修 bug 之前先有一条能在这个 bug 上变红的命令（失败测试、curl、脚本）。然后最小化复现，列 3 到 5 个可证伪的假设，用带唯一前缀的日志逐个验证。根因写进计划，回归测试作为第一个子任务，修复放在后面的子任务，最后清掉临时日志。造不出回路就停下说明，向用户要复现环境或日志。

## 完成标准

- 设计确认与拆解确认都有记录，`stage: ready-for-dev`。
- 每个新表 / 字段 / 状态 / 配置键都有存在性结论；涉及外部系统的卡，「外部事实与未知项」已列出且未核实项有处置。
- 复杂卡的设计各节齐全，契约一节存在，AC 追踪表没有缺口。
- 每张子任务单都能被没有上下文的执行者独立执行，预演过的单子没有歧义。
- 本窗口没有改业务代码，没有写迁移脚本。

## 常见错误

- 把"对齐通过"当成开发许可，在计划窗口顺手写代码或建分支。
- 设计只写"新增 X 表"，不写列、索引、量级；上线后才发现表建多了、建错了，已在 dev 执行的迁移改不回来。
- 子任务单写"参照上文""按我们刚才讨论的"，执行者看不到上文。
- 让低端模型做事务、并发、幂等类子任务，又不给精确的用例。
- 同一批次的两个子任务改同一个文件。
- 测试夹具手写，不用真实响应，线上字段对不上。
- 设计只加不减：每个候选结构都留着，精简要等事后改版；先过存在性门。
