# 05 · 卡级代码评审（Card Review）

本卡全部子任务通过、集成评审通过之后，**推送之前**，对整张卡的改动做一次两轴评审。推送到远端主分支会触发 dev 部署，是单向门；评审必须在它前面。产物：卡目录 `05-card-review.md`（模板 `.ai/templates/card-review.md`）。

做法借自 mattpocock/skills 的 code-review（两轴、并行、全新上下文、不合并结论）与 Trellis 的 trellis-check（复用、跨层、范围纪律，机械问题就地修、设计问题停下）。

## 两个角色

- **组织者**：05 协调窗口（顶级模型）。钉住评审范围、派发两轴、汇总、分流发现。
- **评审者**：每轴一个，**全新上下文**，没看过写代码和做计划的对话。首选子代理；工具不支持子代理时，请用户开两个新窗口，分别输入 `card-review <卡目录> spec` 和 `card-review <卡目录> standards`。两种方式读同一份手册、同一份评审范围，等价。评审者只读、只写报告，不改代码。

## 1. 钉住评审范围（组织者）

本仓库直接在主分支开发，中间夹着别人的提交，**不能**用 `git diff <默认分支>...HEAD`。评审范围是本卡的提交清单：

```bash
git log --oneline --grep='\[<卡号>\]'           # 与 05-dev-log.md"提交记录"核对，取并集
git show --stat <提交号>                        # 逐个确认能解析
```

- 清单为空、某个提交解析不了、或与 `05-dev-log.md` 对不上：停下查清，不要带着错的范围开审。
- 跨仓库的卡两个仓库各列一份。
- 把提交清单写进 `05-card-review.md` 的"评审范围"，评审者只按这份清单读 diff（`git show <提交号>`）。
- 本卡现行文档回写的提交也纳入范围；尚未提交的回写先按提交规则处理，再钉住范围。已批准的设计版本及被审阅文档的修订写进评审记录；评审后发生的相关文档修正补入范围并复审对应项。

## 2. 派发两轴（组织者）

派发只给指针，与用户在新窗口里输入的话等价：

```
你是本卡的 <spec|standards> 评审者。按 <仓库>/.ai/workflow/05-card-review.md 的"<Spec 轴|Standards 轴>"一节，评审 <卡目录>/05-card-review.md 里"评审范围"列出的提交。只读，不改代码，报告写进该文件对应一节。
```

两轴并行，互不等待。不在派发语句里附加聊天中的说明。

## 3. Spec 轴（评审者）

输入：`03-alignment.md`（AC、范围内外、决议）、`04-dev-plan.md`（契约、AC 追踪、单向门、「批准后的变更」）、`05-dev-log.md` 的偏差段、评审范围里的提交。实现与已批准偏差一致的不算问题。

报告三类，每条引用 AC 编号或契约原文：

- **缺**：AC 或契约要求了、diff 里没做或只做了一部分。
- **多**：diff 里有、AC 和计划都没要求的行为（范围蔓延）。
- **错**：看起来做了，但实现与 AC 或契约不符（口径、边界、时机、计数、幂等语义）。

## 4. Standards 轴（评审者）

输入：`spec/index.md`"质量检查"指向的规范（至少 `conventions.md`、`testing.md`、涉及上下游时 `integrations.md`、`legacy.md` 相关条目）、[最小实现与修复原则](implementation-principles.md)、`04-dev-plan.md` 的“文档影响与回写”及适用的修复核查 / 简化边界、[项目文档维护](documentation.md)、评审范围里的提交。

逐项看：

- **仓库规范**：违反哪条就引用哪条（文件 + 规则），这是硬违规。
- **文档与实现**：对照实际改动检查文档清单有无遗漏；受影响的现行实体、接口、配置和行为是否准确，旧口径是否已移出当前说明，来源与验证范围是否真实，契约镜像是否同版。核对“无需更新”的原因；已实现行为未写回或未实施方案被写成事实属于必改。当前代码与已批准目标冲突时分别指出，不靠修改规范掩盖实现缺陷。
- **复用**：新写的工具类、常量、映射，仓库里是否已有同类（`grep` 证据）。只有代表同一个稳定概念、调用方必须一起改的重复才建议抽取；恰好相等的两个字面量不抽。
- **跨层数据流**：改动跨三层以上时，读链路（存储 → Service → 接口 → 页面）和写链路逐层核对类型、字段名、错误传递；时区按本仓库时间约定。
- **范围纪律与修复位置**：顺手整理了无关代码；为不存在的场景加抽象、配置或兜底。行为缺陷对照 [调用链核查](implementation-principles.md#修复前核查调用链) 检查相关入口、根因证据、修复归属及回归覆盖，既查共享行为遗漏，也查不同调用方语义是否被错误合并。
- **过度设计**：对照 [最小实现阶梯](implementation-principles.md#最小实现阶梯) 与 [项目设计默认值](../spec/conventions.md#设计默认值) 检查：缺复用（重写仓库已有）、自造标准库 / 平台能力已覆盖的东西、无当前用途的抽象、配置与样板；短代码不能抵消验收、兼容性或测试缺口。
- **简化边界**：有意简化时按 [边界规则](implementation-principles.md#有意简化的边界) 核对当前足够的依据、已知上限、可核查的重新评估条件，以及持续限制是否已回写到现行主记录。已经触发的条件须评估影响；阻塞本次验收的问题不能以“后续优化”放行。
- **测试**：新逻辑有单测；修 bug 有回归测试；期望值不是把实现再算一遍；外部接口夹具来自 `research/` 的真实响应；解析 / 匹配 / 编码类改动检查特殊字符（`+`、空格、大小写）边界用例是否缺失。
- **坏味道基线**（Fowler《重构》第 3 章，全是判断题，仓库规范明确允许的就不报）：命名不达意、重复代码、依恋情结、数据泥团、基本类型偏执、重复的 switch、霰弹式修改、发散式变化、夸夸其谈的通用性、过长的消息链、中间人、被拒绝的遗赠。报的时候写"可能是 X"，并引用代码片段。

工具已经强制检查的（编译、格式）不报。

## 5. 报告格式（评审者）

每条发现一行：

| # | 文件:行号 | 发现 | 依据（AC / 契约 / 规范条目 / 坏味道名） | 严重度 |
|---|---|---|---|---|

严重度三档：**必改**（违反 AC、契约、仓库规范，或会出错）/ **建议** / **判断题**（坏味道类）。每轴 400 字以内，没有发现就写"无"。

## 6. 汇总与分流（组织者）

- 两轴报告原样放在 `05-card-review.md` 各自一节，**不合并、不重新排序**：一轴全过不能抵消另一轴的问题。结尾一句话：每轴发现数，以及每轴内最严重的一条。
- **必改 · 机械性**（漏改一处、日志前缀、缺一个用例、命名）：开一张"返工"子任务单派给执行者，或组织者直接改并记录；改完只复审相关条目。
- **必改 · 设计性**（改表、改接口、改事务边界、改模块归属）：写证据和建议，停下交给用户；要改设计就退回 04。不擅自重写。
- **建议 / 判断题**：列给用户，由用户决定改或不改，结论写进报告。
- 全部必改项关闭后，结论为"通过"。之后才给出推送建议，推送仍由用户确认。

## 完成标准

- `05-card-review.md` 有评审范围、两轴报告、分流结论，结论为"通过"。
- 必改项都已关闭（改了、复审过），建议与判断题都有用户的处理结论。
- 本卡文档影响已核对，相关修正包含在评审范围与复审记录中；未核实的部署状态未被写成已验证。
- 本卡提交仍未推送，或用户在评审通过后确认推送。

## 常见错误

- 让写代码或做计划的窗口自己评审，而不是全新上下文。
- 没读 `04-dev-plan.md`「批准后的变更」与 `05-dev-log.md` 偏差段，把已批准的偏差当成问题报。
- 用分支 diff 圈范围，把别人的提交也审了进去，或漏了本卡的提交。
- 把两轴结论合成一张表按严重度重排，Standards 全过掩盖了 Spec 缺项。
- 评审者直接动手改设计。
- 评审之前就推送了，发现问题时迁移脚本已在 dev 执行。
