# 会话协议（Session Protocol）

完整流程默认一个窗口只做一个阶段；用户启动 `align` 后，允许在本卡 02 澄清与 03 对齐之间连续进行需求问答。轻量维护由 `maintain` 启动，按 [维护协议](maintenance.md) 在一个窗口内连续完成授权范围内的核实、修复、验证与评审。窗口就是一次 AI 会话，工具和模型都可以换（Kimi、Codex、Claude Code、Cursor 等）。所有窗口遵守同一套开场与收尾动作，进度逐轮落档；换窗口只靠卡目录文件交接，不靠聊天记录。

## 在哪里启动

- 在**主改动仓库的根目录**启动 AI 工具（跨仓库卡通常是主改动仓库）。多数工具只从启动目录加载 `AGENTS.md` 和 skill 目录（`.agents/skills/`、`.claude/skills/`）；在两个仓库的上层目录启动，入口与阶段命令都不会加载。
- 执行子任务时，在子任务单写明的"工作目录"启动（可能是另一仓库，或本地临时 worktree）。

## 开场（每个窗口都做）

1. **确定卡目录与路径。** 已有卡来自命令参数；未指定且无法确定时列出未归档卡的 `workflow` / `stage` 请用户指定。新任务按 `card-intake` 或 `maintain` 的建卡规则处理。先读 `workflow`，缺省为 `full`；未知值先查明，不按标题中的“小修复”猜成轻量。
2. **读取恢复入口并核对 stage。** 读卡目录 `README.md` 的 `stage` 与 [当前恢复摘要](../cards/README.md#当前恢复摘要)，打开本阶段有效产物及批准 / 评审记录指针，核对版本、阻塞和下一步；轻量维护读取 `maintenance.md` 的分流依据和本次授权，不要求 03/04。摘要不是批准证据；与正文冲突时先查证。按下文的流程分流与阶段表确认本窗口能做的事；与用户的命令或说法不匹配时，告诉用户当前该执行哪个命令，然后停。执行者的开场与输入范围仍以 `05-execute-subtask.md` 为准。
3. **同步代码。** 完整协调窗口按项目约定 `git pull`（主分支开发），冲突先解决；轻量维护先按其协议核对工作区与安全同步方式。**执行者窗口不 pull**：worktree 的本地临时分支没有上游，主工作区同步由协调窗口负责。
4. **只依据文件，按需读取。** 读该阶段手册要求的输入及其相关章节，不依赖聊天记录，包括本工具以前的会话。旧交接、历史卡和 journal 仅在追溯证据时检索；旧卡没有恢复摘要时，从现有 stage、阶段产物和批准记录恢复，再按已知事实补摘要，不编造缺失记录。

读取时区分现行文档、本卡目标和历史记录；发现文档与实现冲突时按 [项目文档维护](documentation.md) 查证与分流，不能仅按文件日期选结论。

`workflow: maintenance` 且 `stage` 为 `intake` / `in-dev` 时用 `maintain`；`done` 只供追溯，新问题另建关联记录。维护卡不套用下表；命中升级条件先按维护协议切换为 `full`，再核对相应命令。已有完整卡不因输入 `maintain` 自动降级。

下表适用于 `workflow: full`（含缺省）：

| `stage` | 本窗口能执行的阶段命令 |
|---|---|
| 无卡目录 | `card-intake` |
| `intake` | `clarify` |
| `clarifying` | `clarify`；也可用 `align` 整理已有共识或吸收新信息并继续讨论，无需 BA 问卷 |
| `aligning` | `align`（包含与 Dev 沿设计树继续讨论）；也可显式用 `clarify` 补充澄清 |
| `planning` | `dev-plan` |
| `ready-for-dev`、`in-dev` | `develop`；`execute-subtask`（子任务状态须为"待执行"或"返工"）；`card-review <卡目录> spec` / `standards`（`in-dev`，集成评审已通过） |
| `desk-check` | `desk-check` |
| `in-qa` | `qa-handoff` |
| `done` | 无，卡已归档 |

02 的交互轮次可以在同一窗口继续；首次进入 03 由用户输入 `align`。此后发现新问题或解锁待展开题时，先保存明确答复与草稿，改为 `clarifying`，直接复用 02 的设计树规则追问，答复后继续回填与复核，无需用户切换命令或重新开场。准备整理共识或仅等待已审阅的业务问题答复时回到 `aligning`；需要业务判断才给 Dev 审阅具体问题并自行转发，无需先有 BA 问卷。每轮简述关键变化、依据与下一步，不能把回复结束当作需求收敛。后续阶段发现影响已批准需求的关键问题时，按 `overview.md` 回流，修订重新批准前不继续依赖旧结论的实现。

## 收尾（每个窗口都做）

1. 本阶段产物写进卡目录；同步更新 `README.md` 的 `stage` 与当前恢复摘要：有效产物、阻塞、下一步、恢复阅读。已失效的进度移出入口，过程与依据保留在阶段记录；执行者窗口不改 `README.md`，见 `05-execute-subtask.md`。
2. 按 `journal/README.md` 追加 journal 条目。执行者窗口可以省略，由协调窗口汇总。
3. 打印"下一步"，然后结束本轮：

   ```
   下一步
   - 卡目录：.ai/cards/<卡目录>/
   - 当前 stage：<值>
   - 需要人做的事：<例：与 Dev 讨论待定分支 / 审阅开发计划后回复"计划通过" / 确认提交计划>
   - 下一个窗口：在 <仓库或工作目录> 启动，输入 <阶段命令> <卡目录> [子任务编号]
   - 建议模型：<顶级 / 低端>
   ```

   轻量维护未完成时，下一步写具体阻塞 / 待执行动作，换窗口用 `maintain <卡目录>`；已完成则写交付与归档结果，不提示进入 04。

   仍在需求问答循环中时，下一步写清“与 Dev 讨论本轮 Q”“查证具体事实”或按需“审阅并转发业务问题 / 补充 BA 答复”；只有换窗口时才需要重新输入 `align <卡目录>`。关键问题收敛后写“审阅最终摘要并回复对齐通过”，获批准后再给出 `dev-plan` 入口。

## 不可让步

- **完整流程中，`align` 内允许连续进行 02–03 的需求问答；其余阶段由用户显式触发。** "继续""没问题就开发""按计划做完"都不能放行开发计划或实现。
- 完整流程除上述需求问答循环外，用户坚持在同一窗口继续下一阶段时，必须显式输入该阶段命令；AI 按该阶段的开场重新执行（重读文件、核对 `stage` 与批准记录），不沿用本窗口的推理结论。
- 完整流程的阶段批准必须是 AI 呈现最终摘要**之后**用户发的一条新消息。最初的请求、建卡时的同意、"没问题的话就……"这类条件句都不算批准。

轻量维护的实现授权可以来自已有明确修复请求，按维护记录保存，不要求重复阶段确认；升级后恢复完整流程的批准与阶段边界。

## 阶段中途换窗口

上下文快满、要换工具或交给同事时：

1. 先把进度写进本阶段产物（未完成的项标“进行中”），同步当前恢复摘要，不要只留在聊天里。摘要和阶段产物足够恢复时，不必另写交接文件。
2. 仍有临时工作需要交接时，在卡目录写 `handoff-<日期>-<序号>.md`，同日递增、保留旧文件名与内容。记录当时的卡路径 / stage、有效产物与批准记录指针、进行中的事、阻塞、下一步、必要阅读章节及已知假设。已完成事实不复制正文；不含 token、secret、内部敏感地址或个人敏感信息。README 只指向当前有效交接，旧交接注明后续替代位置。
3. 新窗口先读 README，再读它指向的当前产物和必要交接，不按日期猜“最新结论”。交接是历史快照，不改变 stage 或批准；冲突按 [项目文档维护](documentation.md) 的证据与批准规则处理，查证后修正摘要与指针。

## 权限模式

- 对齐、制定计划、协调评审窗口不要开自动批准（如 yolo）：这些窗口的价值就在人在环。
- 执行窗口可以开自动批准：改动范围被子任务单锁住，结果还要过评审。
