# `decisions/` · 决策记录

两类记忆，都是"为了不再重新争论一遍"。

## `adr/` · 架构决策记录

极简格式（借自 mattpocock/skills 的 ADR 约定）：

```markdown
---
status: accepted   # proposed | accepted | deprecated | superseded by 000N
date: 2026-09-21
---
# <决定的一句话标题>

<1–3 句：背景是什么、决定了什么、为什么。>

（可选）考虑过的替代方案 / 后果，只在值得记住时写。
```

文件名 `NNNN-slug.md`，顺序递增；新增前扫一遍目录取最大号加一。不改旧条目内容；推翻时新写一条并把旧的 `status` 改为 `superseded by NNNN`。

**什么时候写 ADR**：三个条件同时满足才写。

1. 难回头：改主意的代价是实实在在的。
2. 事后会困惑：未来的人看代码会问"为什么这么做"。
3. 真有取舍：当时有别的选择，是为了具体原因选了这个。

只满足一两条就不写；写进 `spec/conventions.md` 或 `spec/legacy.md` 就够。

## `rejected/` · 被否决的需求与方向

按**概念**一文件，不按卡一文件：`<concept-slug>.md`。多张卡请求同一件事，都记在同一个文件里。

```markdown
# <概念名>

<一两段：这个方向是什么，我们不做。>

## 为什么不做

<实质性理由：范围、架构约束、业务规则、成本。避免"现在没时间"这类临时理由，那是推迟不是否决。>

## 历次请求

- DEMO-123（示例月份）：<一句话>
- DEMO-150（示例月份）：<一句话>
```

**什么时候写**：对齐阶段 BA 否决了一个 feat 方向，或 AI 的价值质疑被采纳导致某方向被砍。只记"否决"，不记"已经实现所以不用做"。

**什么时候读**：读卡阶段（01）核实"是否曾被否决"；同类需求再来，先把这个文件给 BA 看，问"当时的理由还成立吗"。BA 改主意就删掉或改写该文件，让新卡正常走流程。
