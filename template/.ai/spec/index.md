# `spec/` 索引 · 开发前必读与质量检查

规范按主题分文件；本索引按**触发条件 → 文件 / 确切章节 → 读取目的**组织。索引负责导航，约束正文仍在被指向的文件中。

现行事实与工程约定的维护、历史去向、证据和冲突处理，统一按 [项目文档维护](../workflow/documentation.md)。完整卡未来方案保存在已批准的 03/04，轻量维护目标与授权在 `maintenance.md`；实施后更新相关现行段落。“完成”只表示文档已建立，读取关键事实仍须核对其适用修订与证据。

## 阅读指针怎么写

- 文档优先用相对链接定位到真实标题；短文件可以整份引用，长文件必须缩到相关章节。章节重命名或文件移动时同步修正引用，不只写一个未经核实的章节名。
- 源码指针注明仓库、仓库相对路径与类 / 方法等符号；行号仅作辅助。共享契约注明主来源和适用修订。读取目的说明本卡要遵守什么或核实什么，不复制整段规则。
- 完整流程在 04“开发前已读”记录适用规范、契约及核实结果，子任务只携带相关指针；轻量维护将必要指针记入 `maintenance.md`。规范默认以三份左右为精简目标，必要约束超出时写明用途并保留，不因数量删掉契约、测试或安全要求。
- 路径不存在、章节找不到、正文仍是占位或与实现冲突时，先查证并修正指针；未解决的必要缺口按 [项目文档维护](../workflow/documentation.md) 记录并处理，不能勾选“已读”后凭猜测继续。

## 开发前按任务类型必读

下表是接入起点：模板中尚待填写的 spec 先链接到文件，不假设其中已有章节。接入时按项目实际内容改成准确的章节链接并核实，完成前保留“待写”状态。新增项目特有行也使用相同的三列。

| 触发条件 | 文件 / 章节 | 读取目的 |
|---|---|---|
| 任何新增 / 修改代码 | [代码归属](code-placement.md)、[编码约定](conventions.md) | 确认改动位置、依赖边界和最小实现要求 |
| 制定开发计划 / 技术设计 | [编码约定](conventions.md) 中接入后已建立的设计默认值、最小实现阶梯 | 先核对已有约定，再判断哪些设计确有必要 |
| 新增或修改接口 | [编码约定](conventions.md)、[架构](architecture.md)、[接口契约](../context/api-contract.md) | 定位接口配方、请求链路与受影响的契约章节，核对边界和兼容性 |
| 新增实体 / 字段 / 表 | [编码约定](conventions.md)、[领域](domain.md)、[历史包袱](legacy.md) 中相关条目 | 核对数据语义、迁移方式、状态约束和已有风险 |
| 新增或修改定时任务 / 异步任务 | [编码约定](conventions.md)、[架构](architecture.md) | 定位任务配方与执行链路，核对并发、失败和重入约束 |
| 改某个上下游集成 | [集成](integrations.md)、[上下游](../context/upstream-downstream.md) 中对应系统 | 核对代码入口、外部约束及尚需确认的问题 |
| 改配置键 / 部署清单 | [配置与部署](config-and-deploy.md)、[决策目录](../decisions/README.md) 中适用 ADR | 找到配置来源、发布前置和仍然有效的取舍依据 |
| 修任何 bug | [历史包袱](legacy.md) 中同模块条目、[测试](testing.md)、按路径选 [完整流程反馈回路](../workflow/04-dev-plan.md#fix-卡的反馈回路) 或 [轻量维护验证](../workflow/maintenance.md#执行与验证) | 查已有坑，建立复现与回归证据；不将完整设计要求机械套入轻量维护 |
| 任何跨仓库的改动 | [接口契约](../context/api-contract.md#来源与适用范围)、[契约位置](../context/related-projects.md#共享契约的位置)、[跨层与跨仓库清单](guides.md#跨层与跨仓库) | 找到主来源与适用版本，再读取本卡涉及的契约正文 |

通用工程约束和 [思考清单](guides.md) 始终适用；其余按触发条件读取相关章节。历史卡、旧方案和日志仅在需要证据时检索，不默认全文加载。

## 质量检查（提交前）

1. `git diff --name-only` 看改了什么，对每个改动区域回头读对应规范。
2. `<门禁命令>` 绿。
3. 测试：新纯逻辑 → 单测；bug → 回归测试；改了行为 → 更新既有测试。
4. 逐项核对本卡适用规范。本节是通用提交前检查入口；项目另有检查清单时在此补充真实链接，不依赖未建立的“提交前清单”章节。
5. 有没有要写回 `legacy.md` / `guides.md` / `../decisions/` 的新知识。
6. 核对本卡的文档影响记录（完整流程在 `04-dev-plan.md`，轻量在 `maintenance.md`）：已实现变化对应的现行文档已更新，证据与验证范围准确；无需更新的项有原因。受影响的引用及契约镜像已处理，不以镜像相同代替事实核验。
7. 对本次受影响的文档与引用执行 [文档检查](../workflow/documentation.md#文档检查)，将缺口纳入现有评审记录。
