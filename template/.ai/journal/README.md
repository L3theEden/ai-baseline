# `journal/` · 会话日志

记录每次 AI 协作会话做了什么、发现了什么、教训是什么。日志保存历史脉络，当前任务从卡 README 的恢复摘要进入，长期知识从 spec / context / decisions 读取。

## 文件组织

- 按开发者分目录：`journal/<git user.name>/YYYY-MM.md`。多人并行不冲突。
- 每个会话结束追加一条，条目模板见 [journal-entry](../templates/journal-entry.md)。标题保留真实日期、卡号和阶段；同日同卡同阶段的多次会话加序号，便于唯一定位。
- 单文件接近约 500 行或已明显影响查找时，**在同一个月续卷**：首卷保留 `YYYY-MM.md`，后续依次为 `YYYY-MM-part-02.md`、`YYYY-MM-part-03.md`。下一月才使用新的月份；单条会话记录尽量完整保留，不为凑行数切断。此命名为格式说明，不要求预建空文件。
- 已有日志不为改名而批量搬迁。发现旧卷月份与条目日期不一致时，保留原文，在索引标明实际日期范围，后续按正确月份续写。

## 轻量索引与检索

一个月只有短日志时可直接按日期、卡号、主题检索，无需额外建索引。出现分卷或查找困难时，在该开发者目录维护 `index.md`，每卷一行：

| 月份 | 卷文件（相对链接） | 实际日期范围 / 主要主题或卡号 |
|---|---|---|

索引只负责定位，不复制条目正文、任务进度或提炼状态。新建卷时登记，追加新主题时按需补充；需要单条证据时链接到唯一标题。移卷或卡片归档后修正受影响的现行链接。新会话先从当前卡恢复，只有追溯时才通过索引或关键词读取相关历史。

## 什么时候写

- 完整流程每个阶段结束时（哪怕只是读卡）；轻量维护本次会话结束或交接时记一条，引用 `maintenance.md` 的结论与证据。
- 会话交接前。
- 发现了值得记的坑，哪怕卡还没结。

## 每月提炼

每月（或每个迭代结束）按索引与卡号复查本期日志及仍待处理的旧项，判断：重复出现的坑是否进入 `spec/legacy.md` / `spec/guides.md`，约定是否进入 `spec/conventions.md`，真实取舍是否进入 `decisions/adr/`，可复用上下文是否进入 `context/`。

去向统一维护在原条目的 **“已回写到”** 字段，逐项选择下列状态，不另建台账：

- **待处理**：事项、拟写入的文件 / 章节、缺少什么依据或何时继续处理。
- **已沉淀**：实际目标文件 / 章节及核实依据；目标内容已存在并已核对后才能标记。
- **无需沉淀**：原因，例如仅为本卡过程，或已有规范覆盖并附指针。

一条会话有多项教训时分别记录，不能因其中一项已写回就把其余一并标为完成。兼容旧的“已回写到：路径”与 `[已提炼 → spec/xxx.md]` 写法，复查时核对目标再补状态；只更新去向，不改原始事实和决议，不删除历史条目。没有可复用内容时写明无需沉淀的原因。

本卡已实现事实的必需回写仍按 [项目文档维护](../workflow/documentation.md#随开发维护) 在开发与评审时完成；轻量维护将结果记入维护记录，同样不能以“待处理”推迟到月度整理。

## 不写什么

- 不写 token、密码、secret、内部敏感地址、个人敏感信息或未脱敏业务数据。需要追溯时引用项目内受控证据的位置，不复制敏感内容。
- 不复制大段代码或文档；写指针。
- 不写与本项目无关的个人备忘。

公共模板只保留通用规则与虚构示例，真实日志和业务证据保留在原项目受控位置。
